# lumex/core/framing

Кодеки кадров поверх потока байт: SLIP, COBS, по разделителю, с префиксом длины, с заголовком и контрольной суммой, Modbus RTU и конвейеры стадий.

## Фаззинг

С `LUMEX_BUILD_FUZZERS=ON` (Clang, `LUMEX_BUILD_TESTS`) для каждого кодека и для конвейера собирается цель libFuzzer в `lumex/tests/fuzz/framing/` с AddressSanitizer: `fuzz.framing.slip`, `cobs`, `delimiter`, `lengthprefix`, `header`, `modbusrtu`, `pipeline`. CTest запускает каждую на 30 секунд под меткой `fuzz` (`ctest -L fuzz`).

Вход - `[вариант][план кусков][поток]`; вариант выбирает опции кодека (предел кадра, порядок байт, ширину поля длины, вид контрольной суммы, таблицу функций Modbus), одинаковые проверки лежат в `LumexFramingFuzzSupport.hpp`:

- поток, поданный целиком, по кускам плана и после `reset ()`, дает одни и те же кадры и ошибки в том же порядке; приемник только кадров слышит ровно кадры приемника с ошибками;
- каждый выданный кадр не больше `max_frame_size` опций, каждая ошибка относится к `framing_errc` и приходит с пустым кадром;
- выданный кадр кодируется и свежий декодер возвращает ровно его; для кодеков с однозначной формой кадра (`delimiter`, `length_prefix`, `header`, `modbus_rtu`) закодированные байты стоят в потоке как есть;
- поток как нагрузка либо отказывает с `payload_too_large` и не меняет выход, либо возвращается из свежего декодера одним кадром (пустой кадр SLIP и кадр с разделителем в `delimiter_codec` кодек не переносит).

Начальный корпус цели пишут сами при запуске: кадры, которые кодек делает из синтетических нагрузок (с особыми байтами, 254 и 255 байт для COBS, обрезанные копии). Файлов векторов в репозитории нет. Найденное становится модульным тестом набора `framing` с минимальными синтетическими байтами.
