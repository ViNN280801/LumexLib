\page Protocol Протокол: описание протоколов обмена таблицей

## Обзор

Модуль `lumex/core/protocol` (цель `lumex::protocol`, опция `LUMEX_BUILD_PROTOCOL`) описывает протокол обмена с прибором один раз, таблицей на X-макросе. Из таблицы библиотека получает типы команд с полями, ключом, ответом и опциями, имена из спецификации, описания, имена полей, записи для индекса времени выполнения и методы клиента, названные по строкам таблицы, а также кодирование и декодирование полей в трех раскладках: двоичной, текстовой с полями фиксированной ширины и текстовой с разделителями. Модуль не выполняет ввод-вывод: кадры собирает `core/framing`, обмен ведет `applied/transport`.

Модуль работает начиная с C++11 и подключается одним заголовком:

```cpp
#include "lumex/core/protocol/LumexProtocol"
```

Сейчас в модуле есть ядро описания (макросы, опции, записи, защита от макросов платформы), все типы полей, три раскладки с кодированием и декодированием и коды ошибок. Реестры параметров (`LUMEX_PROTOCOL_REGISTRY`), индекс времени выполнения с поиском по ключу и кадру, `describe`, контекст сеанса и экспорт в Markdown и JSON описаны ниже.

## Сборка

| Опция | По умолчанию | Назначение |
| --- | --- | --- |
| `LUMEX_BUILD_PROTOCOL` | `ON` | Собирать модуль (требует `reflection`, `expected`, `span`, `string_view`, `utility`) |
| `LUMEX_PROTOCOL_WITH_JSON` | `ON` | Определить макрос `LUMEX_PROTOCOL_WITH_JSON` для потребителей модуля: заголовок `export/LumexProtocolExportJson.hpp` (`export_json`) собирается с nlohmann/json потребителя; без опции заголовок отказывается компилироваться, остальной модуль не меняется |
| `LUMEX_BUILD_FUZZERS` | `OFF` | Цели libFuzzer в `lumex/tests/fuzz` (только Clang, нужен `LUMEX_BUILD_TESTS`): `fuzz.protocol.layouts`, метка CTest `fuzz` |

Библиотека компилируется ради одного объекта: категории ошибок `"lumex.protocol"` (`LUMEX_PROTOCOL_API`). Поэтому код ошибки, созданный в одной DLL, равен перечислителю в другом модуле процесса. Макросы, шаблоны, поля и раскладки находятся только в заголовках.

Модуль не зависит от `core/framing`: порядок байт полей берется из `lumex/core/utility/bit/LumexByteOrder.hpp` (тот же тип `framing::codec::byte_order`), а кодек кадров протокол только называет параметром типа. Транспорт с кадрированием (`applied/transport`) соединяет оба модуля.

## Таблица

Протокол задается одним макросом-списком с двумя параметрами: `X` для строки, у которой идентификатор совпадает с именем из спецификации, и `X_AS` для строки с другим идентификатором:

```cpp
namespace widget
{
enum class state { idle, busy };

LUMEX_PROTOCOL_LAYOUT (status_t, (u8_, u16_le_<scale<std::ratio<1, 10> > >),
                       ("mode", "temperature"));

#define WIDGET_ROWS(X, X_AS)                                                  \
  X (PING, 0x01, "Проверка связи", (), (), (), (idempotent))                  \
  X (SET_RATE, 0x02, "Частота измерений",                                     \
     (u16_le_<scale<std::ratio<1, 100> > >, u8_), ("rate", "channel"),        \
     (status_t), (timeout (500), retries (2), accepted_in (state::idle)))     \
  X_AS (ERASE_LOG, "DELETE", 0x03, "Очистка журнала", (), (), (status_t),     \
        (dangerous))

LUMEX_PROTOCOL_DEFINE (widget_v1, my_codec, my_header, WIDGET_ROWS);
}
```

Строка: `X (идентификатор, ключ, описание, (поля...), (имена полей...), (ответ), (опции...))`; `X_AS` принимает имя из спецификации вторым аргументом. Каждая группа заключена в скобки и может содержать сколько угодно элементов с любыми запятыми внутри (`std::ratio<1, 100>`). Группа раскрывается один раз в список аргументов шаблона, поэтому ни число полей, ни число строк не ограничено: в тестах есть список из 100 строк и раскладка из 40 полей всех видов. Каждый макрос пишется с точкой с запятой после него.

Имена в таблице (`u8_`, `scale`, `timeout`, `dangerous`, `level::debug`) не требуют пространства имен: группы вычисляются внутри класса, производного от словаря таблицы (`dsl::vocabulary`). Типы и перечисления пространства имен таблицы (раскладки, состояния прибора) тоже видны. Слово словаря скрывает тип пользователя с тем же именем: раскладку `stream` или перечисление `level` в таблице пишут с пространством имен (`::widget::stream`); если группа полей или ответ называет слово словаря, макрос сообщает об этом своим сообщением.

Ключ строки: целое, символ, перечислитель или текстовая мнемоника (`"AZ"`, хранится как `dsl::text_key`).

## Что получается из строки

Для строки `SET_RATE` в протоколе `widget_v1`:

| Член | Значение |
| --- | --- |
| `widget_v1::SET_RATE_t::fields_type` | `dsl::field_list<...>`: типы полей (`::types`) и их число (`::count`) |
| `reply_type` | тип ответа или `dsl::no_reply` |
| `key ()`, `key_type` | ключ, константа |
| `options ()`, `options_type` | опции, константа (`dsl::option_set<...>`) |
| `identifier ()` | `"SET_RATE"` |
| `specification_name ()` | `"SET_RATE"`; для строки `X_AS` строка из таблицы (`"DELETE"`) |
| `description ()` | описание из таблицы |
| `field_names ()` | имена полей по порядку (`dsl::names_t`) |

При компиляции проверяются: число имен полей; что каждый элемент группы полей является полем; что ответ является полем, раскладкой или видом ответа другого слоя (тип с `typedef dsl::reply_tag lumex_protocol_reply;`); что группа не называет собственный тип строки (строка `status` и раскладка `status_t`: внутри строки имя `status_t` означает саму строку) и не называет слово словаря.

Сам протокол дает `protocol_name ()`, `framing_type`, `header_type`, `base_protocol` (`void` у корня), список команд `dsl::commands_of<P>::type` в порядке таблицы, их число `dsl::command_count<P>::value`, записи времени выполнения `dsl::command_entries<P> ()` и примесь клиента `P::lumex_methods<Client>`: метод на каждую строку с именем идентификатора (`client.SET_RATE (20, 1)`), который вызывает `Client::lumex_invoke<Row> (args...)`.

## Опции строки

| Опция | Значение |
| --- | --- |
| `timeout (ms)` | ответ должен прийти за столько миллисекунд |
| `retries (n)` | сколько раз повторить запрос после таймаута |
| `idempotent` | повтор строки ничего не меняет |
| `dangerous` | строка необратимо меняет прибор, нужно подтверждение |
| `deprecated` | строка оставлена для старых приборов |
| `stream (interval_ms)` | прибор сам присылает строку с этим интервалом |
| `accepted_in (s1, s2, ...)` | прибор принимает строку только в этих состояниях |
| `log_level (level::...)` | уровень записи лога для строки |
| `firmware (from, to)` | строка есть в версиях прошивки с `from` по `to` включительно |
| `model ("A", "B")` | строка есть только у этих моделей |

Опции хранятся как типизированные константы: `dsl::get_option<dsl::kind::timeout> (C::options ()).milliseconds`, `dsl::has_option<dsl::kind::model> (...)`, `dsl::flags_of (...) & dsl::row_flags::dangerous`. Все запросы работают в `static_assert`. Опция, указанная дважды (кроме флагов), и значение, которое не является опцией, не компилируются.

## Поля

Поле описывает логическое значение (ширину, знак, порядок байт, масштаб, единицу), а раскладка протокола решает, как оно выглядит в сообщении. Простые поля пишутся с угловыми скобками и без них (`u8_` и `u8_<>`).

| Поле | Значение после декодирования |
| --- | --- |
| `u8_`, `i8_`, `u16_le_`, `u16_be_`, `i16_le_` ... `u64_be_`, `i64_le_`; 24-битные `u24_le_`, `u24_be_`, `i24_le_`, `i24_be_` | целое; с `scale<...>` значение `fixed_point`: `raw` (как на проводе) и `value ()` (инженерное) |
| `f32_le_`, `f32_be_`, `f64_le_`, `f64_be_` | `float` или `double` (масштаба нет, единица есть) |
| `sign_magnitude_<i32_be_>` | целое со знаком: старший бит знак, остальные модуль |
| модификаторы `scale<std::ratio<N, D> >`, `unit::microliter` и другие (`LUMEX_PROTOCOL_UNIT` для своей единицы) | масштаб и единица для лога и экспорта |
| `ascii_hex_<W>` | `W` шестнадцатеричных цифр, целое без знака |
| `dec_text_<I, F>` | десятичное число с точкой (`000500.000`), `fixed_point` в единицах последней цифры |
| `char_` | один символ |
| `text_<N>` | текст до `N` символов, дополненный NUL (`fixed_string<N>`) |
| `token_` | токен текстовой раскладки с разделителями, в других раскладках остаток сообщения (`text_view`) |
| `bits_<S, first, count, T>` | `count` бит слова `S` начиная с бита `first`; `T`: без знака, `bool`, со знаком или перечисление |
| `mask_<S, mask, T>` | биты слова под маской, собранные подряд (чередующиеся каналы `0x55` и `0xAA`) |
| `split_<S, части...>` или `split_<S, раскладка частей>` | несколько частей одного слова: `raw` и `parts`; при кодировании непокрытые биты берутся из `raw` |
| `enum_<S, E>` | перечисление, хранимое полем `S` (целое, символ); для `LUMEX_DEFINE_REFLECTED_ENUM` неизвестное значение отвергается |
| `array_<T, N>` | `N` элементов (`std::array`) |
| `counted_<T, C, Max>` | счетчик `C`, затем столько элементов, не больше `Max` (`bounded_array`) |
| `computed_count_<T, Expr, Max>`, `count_from_<I>` | число элементов вычисляется из полей раньше (`count_from_<I>`: значение поля `I`) |
| `optional_tail_<поля...>` | поля в конце сообщения, если оно продолжается (`present`) |
| `by_length_<Min, A, B>` | `A`, если осталось меньше `Min` единиц, иначе `B` |
| `union_by_<D, case_<V, L>...>`, `field_<I>`, `at_end_<D>` | вариант по дискриминанту: поле перед вариантом, раньше в группе или в конце сообщения (`union_value`) |
| `union_by_context_<Key, case_...>`, `LUMEX_PROTOCOL_CONTEXT_KEY` | вариант по значению сеанса (`decode_context_t`) |
| `nested_<P, K>`, `layout::decode_nested<P, Row>` | сообщение другого протокола: ключ и байты, которые декодирует строка вложенного протокола |
| раскладка `LUMEX_PROTOCOL_LAYOUT` | запись полей (`field::record<...>`) |

Значения всех полей группы лежат в записи `field::record<F...>`: `field::get<I> (record)`, `field::visit_fields (record, visitor)`. Декодирование не выделяет память: тексты и массивы хранятся на месте, токены и вложенные сообщения являются видами в декодируемый буфер (буфер должен жить, пока используются значения). Описание поля для индекса и экспорта: `field::impl_of<F>::type::info ()` (`field_info_t`: вид, размер, порядок байт, знак, масштаб, единица, число).

Декодер принимает и неканоническую запись и нормализует ее: десятичные цифры с ведущими пробелами или знаком `+`, шестнадцатеричные цифры в нижнем регистре, токены с пробелами по краям, `-0` в поле `sign_magnitude_` (декодируется как 0 и кодируется как `+0`), биты слова вне частей `split_` (сохраняются в `raw`). Поэтому повторное кодирование может дать другие байты, но после одного кодирования запись устойчива. Значения массивов (`array_`, `counted_`, `computed_count_`) хранятся на месте и живут на стеке вызывающего: значение больше 64 КиБ не компилируется.

У `by_length_<Min, A, B>` единица длины своя у каждой раскладки: байты в двоичной, символы в текстовой фиксированной ширины (целое из двух байт это четыре шестнадцатеричных символа), токены в текстовой с разделителями. Слой, который переносит строку с `by_length_` в раскладку с другой единицей, повторяет эту строку со своим `Min`. При кодировании выбранная форма должна оказаться по свою сторону `Min`, иначе `invalid_value`.

Поля, которые зависят от длины сообщения (`optional_tail_`, `by_length_`, `union_by_<at_end_<D>, ...>`, `nested_`, а также `token_` вне текстовой раскладки с разделителями), должны быть последними в своей группе; это проверяется при компиляции.

## Раскладки

Раскладку протокола выбирает тип заголовка слоя: `P::header_type::layout_type`, если заголовок его называет, иначе `binary_layout<>`. Слой `LUMEX_PROTOCOL_EXTEND_FRAMED` с другим заголовком переносит те же строки (те же типы команд) в другую раскладку, не повторяя их:

```cpp
struct hex_header { typedef lumex::core::protocol::layout::fixed_width_text_layout<16> layout_type; };
#define NO_ROWS(X, X_AS)
LUMEX_PROTOCOL_EXTEND_FRAMED (widget_lan, widget_v1, lan_codec, hex_header, NO_ROWS);
```

| Раскладка | Как выглядят поля |
| --- | --- |
| `binary_layout<>` | байты подряд в порядке поля |
| `binary_layout<natural_alignment<Offset> >` | то же, и при компиляции проверяется, что 2-байтовые поля стоят по четным смещениям, а 4- и 8-байтовые по кратным 4 (от `Offset` байт заголовка, до первого поля переменной длины); `layout::is_aligned<P>::value` проверяет всю таблицу |
| `fixed_width_text_layout<16>` | целое из `n` байт: `2n` шестнадцатеричных цифр его битов (`i16 -1` это `FFFF`), число с плавающей точкой: цифры его битов |
| `fixed_width_text_layout<10>` | целое: десятичные цифры по ширине наибольшего значения, с позицией знака у знаковых (`-005`); числа с плавающей точкой не допускаются |
| `tokenized_text_layout<Sep, KeySep, Radix, Trim>` | ключ строки, затем поля токенами через `Sep` (`2,1250,3,-2`); терминатор сообщения добавляет кодек кадров; с `Trim` пробелы вокруг токенов при декодировании отбрасываются |

## Кодирование и декодирование

```cpp
namespace layout = lumex::core::protocol::layout;
layout::bytes_t out;
layout::encode_result_t sent
    = layout::encode_request<widget_v1, widget_v1::SET_RATE_t> (out, 12.5, 3);
layout::decode_result_t<layout::reply_value_of<widget_v1::SET_RATE_t>::type> reply
    = layout::decode_reply<widget_v1, widget_v1::SET_RATE_t> (
        layout::bytes_view_t (frame.data (), frame.size ()));
```

- `encode_request<P, Row> (out, args...)`: по аргументу на поле; масштабированное поле принимает инженерное значение (округление до ближайшего, половина от нуля), текстовое поле строку. Значение, которое не помещается в поле, дает `invalid_value`; буфер при ошибке не меняется.
- `decode_request`, `decode_reply`, `encode_reply`, `encode_request_record`, `make_request`; для любого поля или раскладки `layout::encode<Layout, F>` и `layout::decode<Layout, F>`.
- Декодер читает только свой вход: короче полей `truncated`, длиннее `trailing_bytes`; счетчик больше вместимости `limit_exceeded` до чтения элементов. Декодированное значение всегда кодируется снова.
- Значения сеанса для `union_by_context_` передаются последним аргументом (`decode_context_t`: функция поиска по имени).

## Расширение словаря другим слоем

Слой над ядром (диалог `applied/transport/protocol`) добавляет свои слова, не меняя ядро: класс, производный от `dsl::vocabulary`, с видами ответа (`ack_nak<...>`) и опциями, и заголовок протокола, который его называет (`typedef my_vocabulary lumex_vocabulary;`) или специализация `dsl::vocabulary_of<Header>`. Опция другого слоя является литеральным типом с `option_kind`, создается функцией `constexpr` и дает `option_name ()` и `view_value ()`: запись времени выполнения перечисляет такие опции в `options.extra`.

## Записи времени выполнения

`dsl::command_entries<P> ()` возвращает по одной записи `dsl::command_entry_t` на команду в порядке списка: идентификатор, имя из спецификации, описание, ключ (`key_value_t`: целое без расширения знака и его ширина в байтах, текст, составной ключ или другой тип), имена полей, наличие ответа и опции простыми значениями (`options_view_t`, состояния `accepted_in` приведены к 64-битным целым, опции других слоев в `extra`). Массив строится один раз при первом вызове.

## Реестры параметров

Многие приборы хранят настройки в таблице, которую читают и пишут несколько общих команд: параметр по номеру, регистр Modbus по адресу, двухбуквенная мнемоника. Такая таблица описывается макросом `LUMEX_PROTOCOL_REGISTRY`, а общие команды остаются обычными строками протокола. Реестр держит имя, ключ, тип значения (одно поле: ширина, знак, масштаб, единица), доступ, пределы и диапазон прошивок или моделей:

```cpp
#define LAMP_PARAMS(P, P_AS)                                                  \
  P (FREQUENCY, (0x10), "Частота вспышек",                                    \
     (u16_be_<scale<std::ratio<1, 10> >, unit::hertz>), RW,                   \
     (limits (1, 100), firmware (2, 7)))                                      \
  P (LEVEL, (0x11), "Яркость", (u8_<unit::percent>), R, ())                   \
  P_AS (REMOVE_ALL, "DELETE", (0x12), "Очистка", (u8_), W, ())
LUMEX_PROTOCOL_REGISTRY (lamp, LAMP_PARAMS);

struct lamp_header
{
  typedef lumex::core::protocol::registry::table_vocabulary lumex_vocabulary;
};

#define LAMP_ROWS(X, X_AS)                                                    \
  X (SET_PARAMETER, 0x20, "Запись параметра",                                 \
     (registry_key_<lamp, u8_>, registry_value_<lamp, 0, i32_le_>),           \
     ("parameter", "value"), (), ())
LUMEX_PROTOCOL_DEFINE (lamp_protocol, my_codec, lamp_header, LAMP_ROWS);

layout::encode_request<lamp_protocol, lamp_protocol::SET_PARAMETER_t> (
    out, lamp::FREQUENCY, 20.0);
```

Строка реестра: `P (идентификатор, (ключ), описание, (тип), доступ, (опции...))`; `P_AS` принимает имя из спецификации вторым аргументом, как `X_AS`. Ключ задается группой: целое число (индекс), `typed (тип, индекс)`, `unit_param (узел, параметр)`, `mnemonic ("AZ")` (или просто строка) и `modbus (адрес)`. Доступ: `R`, `W` или `RW`. Опции: `limits (min, max)` (инженерные значения), `firmware (from, to)`, `model ("A", "B")`.

Реестр это структура: `lamp::FREQUENCY` перечислитель `lamp::id` (по порядку таблицы, `lamp::lumex_end_of_entries` равен числу записей), `lamp::entries ()` дает таблицу времени выполнения `registry::registry_entry_t` (имена, ключ, `field_info_t` типа, доступ, пределы, прошивки, модели). Функции: `find_entry`, `find_duplicate_key`, `check_access`, `check_limits`, `to_raw` (инженерное значение в сырое с округлением от нуля, только для целых типов), `raw_in_range`, `to_engineering`, `entry_available (запись, прошивка, модель)`, `key_to_string`.

Поле `registry_key_<R, F1, F2>` записывает ключ записи реестра как одно или два целых поля (`registry_key_<R, u8_>`, `registry_key_<R, u8_, u16_le_>` для `typed` и `unit_param`) или как текст (`registry_key_<R, text_<2> >` для мнемоники); оно принимает только перечислитель своего реестра, перечислитель чужого реестра не компилируется. Ключ, которого нет в реестре, при декодировании дает `unknown_case`. Поле `registry_value_` требует, чтобы все записи реестра были целыми, знак-модуль или перечислениями (`static_assert`): у записи с плавающей точкой или текстом нет сырого значения, такой реестр держат отдельно, для экспорта и `verify_registry`. Поле `registry_value_<R, KeyIndex, Raw, Needs>` записывает значение: `KeyIndex` номер поля с ключом в той же записи, `Raw` целое поле-носитель, `Needs` нужный доступ (`registry::access_t::write` по умолчанию, `read` для ответа). При кодировании по порядку проверяются доступ (`access_denied`), пределы (`out_of_limits`) и то, что сырое значение помещается в тип записи и в носитель (`invalid_value`); при ошибке буфер не меняется. При декодировании значение `parameter_value_t` несет сырое и инженерное значения и запись (`entry`).

Реестр сравнивается с самоописанием прибора: `registry::verify_registry<lamp> (описание)`, где `описание (номер, device_entry_t &)` заполняет запись прибора с этим номером и возвращает `false` на последней. С `session_context_t` записи, которых нет в прошивке или модели прибора, пропускаются и перечисляются в `verify_report_t::skipped` (`verify_registry<lamp> (описание, 65536, &сеанс)`). Результат `verify_report_t` перечисляет расхождения: записи только в таблице (`missing_in_device`) или только в приборе (`missing_in_table`), имя, ширину, знак, масштаб, пределы и доступ. Сравнивается только то, что прибор сообщил (`size` 0 и признаки `has_*`).

## Индекс времени выполнения

`index::build_index<P, Реестры...> ()` строит индекс слоя `P` (`index::protocol_index_t`), `index::protocol_index<P, Реестры...> ()` дает один экземпляр на программу. Индекс хранит строки в порядке таблицы (`row_t`): запись `dsl::command_entry_t` (имена, описание, ключ, параметры), ключ, приведенный к ширине провода, дескрипторы полей запроса и ответа (`field_descriptor_t`: имя, `field_info_t`, имя раскладки, составные части, роль), вид ответа (`reply_form`), признак события (у строки есть `stream`). Поиск: `find (ключ)`, `find_integer`, `find_text`, `find_name` (имя из спецификации или идентификатор), `find_registry`, и по принятому кадру: `match (кадр)` читает ключ и возвращает строку и смещение, с которого начинаются поля.

Ширина ключа на проводе: константа `static constexpr std::size_t key_width` в типе заголовка слоя, иначе самый широкий ключ таблицы (целый, перечислитель или составной со своим `lumex_key_width ()`). У двоичного слоя и слоя с шестнадцатеричными цифрами фиксированной ширины ширину или свой `key_reader` обязан назвать заголовок: ширина типа ключа (`0x1D` это `int`) не ширина на проводе, и `static_assert` отказывает угадывать. В текстовом слое ключи сравниваются по тексту на проводе: `'A'` это `A`, а `65` это `65`. Ключи таблицы приводятся к этой ширине, поэтому символ `'\xFF'` и число `-1` на однобайтовом проводе один ключ, и два таких ряда индекс отвергает. Ключ из нескольких частей объявляется типом с `typedef dsl::composite_key_tag lumex_composite_key;`, `static std::size_t lumex_key_width ()` и `std::uint64_t lumex_key_bits () const`.

Где в кадре лежит ключ, зависит от раскладки слоя: у `tokenized_text_layout` это первый токен (`index::tokenized_key`), у `binary_layout` первые `key_width` байт (`index::key_at<0, W>`), у `fixed_width_text_layout<16>` первые `2 * W` цифр (`index::key_at_digits<0, 2 * W, 16>`). Другое место называет заголовок слоя: `typedef index::key_at<2, 1> key_reader;` или своим типом со статической `bool read (bytes_view_t, key_read_t &)`.

Одинаковые ключи индекс отвергает. Для целых ключей это проверка при компиляции: `index::keys_unique<P>::value`, `protocol_index<P>` не компилируется с одинаковыми ключами (таблицы больше 200 строк проверяются только при построении). Для остальных (текст, составной, десятичный текст токенизированной раскладки, имена, ключи реестра) `build_index` возвращает ошибку `duplicate_key` с текстом, где названы обе строки и ключ: `protocol p: rows ONE and TWO have the same key 0x07 on the wire`.

## describe

`index.describe (кадр, index::frame_direction::tx, сеанс)` возвращает строку журнала, ту самую, что уровень DEBUG диалога пишет без изменений:

```text
TX widget.SET_SPEED (Set the speed) speed=12.5 rpm
RX widget.STATUS (Read the state) mode=run level=3
TX unknown key=0x15 len=7: 15 01 02 03 04 05 06
RX widget.PING (Liveness check) [decode error: bytes after the last field of a message] len=2: 01 55
```

Поля идут как `имя=значение единица`: масштабированное число печатается инженерным значением (число знаков по масштабу, без хвостовых нулей), перечисление именем (для `LUMEX_DEFINE_REFLECTED_ENUM`, иначе числом), текст в кавычках, флаг `true` или `false`, массив `[a, b]`, раскладка и части слова `{x=1 y=2}`, вариант `case 7: ...`, отсутствующий хвост `absent`, вложенное сообщение `{key='L' len=3}`, запись реестра своим именем и значением с единицей записи (значение записи перечислимого типа `enum_<..., E>` тоже именем элемента перечисления, `registry_entry_t::value_name`). У запроса (`tx`) разбираются поля запроса, у ответа и события (`rx`) поля ответа; ответ-слово диалога выводится длиной и дампом. Неизвестный ключ или пустой кадр дают `unknown` с длиной и дампом, ошибка разбора известной строки добавляет `[decode error: ...]`, длину и дамп. Дамп короче `describe_options_t::dump_limit` (256 байт), текстовое значение (`token_`, `text_<N>`) длиннее `text_limit` (256 символов) режется и получает `... (N chars)` с полной длиной, `show_raw` добавляет сырое значение (`(raw 125)`).

`index::session_context_t` хранит то, что узнано при идентификации: модель, прошивку, слой и именованные значения (`set ("thermostat", 2)`). Декодеры, зависящие от сеанса (`union_by_context_`), читают его через `decode_context ()`; `available (...)` отвечает, есть ли строка или запись реестра в этой прошивке и модели (пока значение не задано, все доступно).

## Экспорт

`index::export_markdown (индекс)` дает документ: заголовок со слоем и его основой, раздел на каждую команду или событие (ключ, описание, ответ, опции, таблицы полей запроса и ответа с видом, шириной, порядком байт, знаком, масштабом и единицей, части составных полей отдельными строками), раздел на каждый реестр и список единиц. Описание строки выводится цитатой (`> `), поэтому его строки не становятся заголовками; `export_json_text` пишет байты, которые не UTF-8, как U+FFFD, а не бросает исключение. `index::export_json (индекс)` (`export/LumexProtocolExportJson.hpp`, макрос `LUMEX_PROTOCOL_WITH_JSON`, nlohmann/json) дает те же данные значением JSON, `export_json_text` текстом. Импорта нет: источником правды остаются таблицы C++.

Опция CMake `LUMEX_PROTOCOL_WITH_JSON` (по умолчанию `ON`) только определяет макрос: заголовок JSON не входит в `LumexProtocol` и собирается с nlohmann/json потребителя, как модуль `applied/json`; каталог nlohmann к цели не добавляется. Без опции библиотека и остальные заголовки собираются без JSON, а подключение заголовка JSON дает понятную ошибку компиляции.

## Макросы платформы и ключевые слова

Идентификатор строки становится именем метода клиента без изменений. Поэтому идентификатор строки проверяется трижды: это не ключевое слово C++ (`delete`, `and`), не макрос в этой единице трансляции (сравнивается текст идентификатора до и после раскрытия макросов) и не имя из списка макросов платформы (`<windows.h>`: `DELETE`, `ERROR`, `IN`, `OUT`, `FAILED`, `min`, `max`, `GetMessage` и другие; заголовки POSIX: `ECHO`, `MIN`, `major`, `minor`), чтобы таблица, собранная на Linux, не ломалась на Windows. Строку с таким именем пишут через `X_AS`:

```cpp
X_AS (ERASE_LOG, "DELETE", 0x03, "Очистка журнала", (), (), (), ())
```

Список отвергает и частые слова протоколов приборов: `ECHO`, `ERROR`, `TEXT`, `IGNORE`, `MIN`, `MAX`, `IN`, `OUT`, `OPTIONAL`, `DELETE`, `TRUE`, `FALSE` и другие. Для таких команд пишут `X_AS (ECHO_TEXT, "ECHO", ...)`.

Список макросов Windows пополняет скрипт `Scripts/CodeTools/protocol_platform_macros.py` (в среде разработчика Visual Studio, `--check` и `--write`): все имена без подчеркивания и все функциональные макросы SDK. `LUMEX_PROTOCOL_CHECK_IDENTIFIERS (LIST);` проверяет список отдельно, `dsl::is_platform_macro_name ("...")` и `dsl::is_cpp_keyword ("...")` отвечают для одного имени.

## Ошибки

`error::protocol_errc` (категория `"lumex.protocol"`): коды ядра от 1 до 99: `truncated` (сообщение короче своих полей), `trailing_bytes` (байты после последнего поля), `invalid_value` (значение, которое тип поля не может представить, или аргумент, который не помещается в поле), `unknown_frame` (кадр не подходит ни к одной строке: другой ключ), `limit_exceeded` (счетчик больше вместимости поля), `unknown_case` (дискриминант не совпал ни с одним вариантом или сеанс не знает значения), `access_denied` (запись реестра не допускает такой доступ), `not_supported` (записи или строки нет в прошивке или модели сеанса), `duplicate_key` (у двух строк таблицы или записей реестра один ключ на проводе), `out_of_limits` (значение представимо, но вне пределов записи реестра). Коды диалога (`timeout`, `retries_exhausted`, `nak`, `refused`, `unexpected_reply`, `not_accepted_in_state`, `link_lost`) добавит слой диалога начиная со 100. Новые коды добавляются в конец своего блока, значения существующих не меняются.

## Ограничения

- Макрос-список строк (`WIDGET_ROWS`, `NO_ROWS`) передают в `LUMEX_PROTOCOL_DEFINE` и `LUMEX_PROTOCOL_EXTEND` его именем без пространства имен: это макрос, и `ns::NO_ROWS` оставил бы `ns::` в коде.
- Пространство имен `index` совпадает с именем функции POSIX `index ()`: псевдоним `namespace index = lumex::core::protocol::index;` пишут внутри своего пространства имен, не в глобальном.
- У строки один ключ и для запроса, и для ответа: если прибор отвечает другим кодом, ответ описывают отдельной строкой.
- Таблицы реальных приборов не входят в библиотеку; протоколы приборов в тестах намеренно изменены по соглашению о неразглашении (NDA).
- `model (...)` и `accepted_in (...)` остаются функциями: тип пользователя с именем `model` в таблице пишут с пространством имен.
- Таблицы определяют в именованном пространстве имен: в безымянном строгий набор предупреждений Clang (`-Wunused-member-function`) отмечает неиспользованные функции строк.
- Время компиляции (синтаксический разбор, медиана из 5, см. `benchmarks/protocol`): заголовки модуля около 300 мс (cl.exe и clang-cl, C++14); список из 100 строк добавляет около 130 мс (cl.exe) и 45 мс (clang-cl), из них около половины проверка идентификаторов строк; раскладка из 40 полей всех видов 43 и 17 мс, а ее кодирование и декодирование в трех раскладках еще 151 и 72 мс.
