\page Protocol Протокол: описание протоколов обмена таблицей

## Обзор

Модуль `lumex/core/protocol` (цель `lumex::protocol`, опция `LUMEX_BUILD_PROTOCOL`) описывает протокол обмена с прибором один раз, таблицей на X-макросе. Из таблицы библиотека получает типы команд с полями, ключом, ответом и опциями, имена из спецификации, описания, имена полей, записи для индекса времени выполнения и методы клиента, названные по строкам таблицы. Модуль не выполняет ввод-вывод: кадры собирает `core/framing`, обмен ведет `applied/transport`.

Модуль работает начиная с C++11 и подключается одним заголовком:

```cpp
#include "lumex/core/protocol/LumexProtocol"
```

Сейчас в модуле есть ядро описания (макросы, опции, записи, защита от макросов платформы), минимальные целочисленные поля и коды ошибок. Полный набор полей и раскладки (двоичная, текст с разделителями, текст фиксированной ширины), реестры параметров, индекс, `describe` и экспорт в Markdown и JSON появятся в следующих частях модуля.

## Сборка

| Опция | По умолчанию | Назначение |
| --- | --- | --- |
| `LUMEX_BUILD_PROTOCOL` | `ON` | Собирать модуль (требует `framing`, `reflection`, `expected`, `span`, `string_view`, `utility`) |

Библиотека компилируется ради одного объекта: категории ошибок `"lumex.protocol"` (`LUMEX_PROTOCOL_API`). Поэтому код ошибки, созданный в одной DLL, равен перечислителю в другом модуле процесса. Макросы и шаблоны описания находятся только в заголовках.

## Таблица

Протокол задается одним макросом-списком с двумя параметрами: `X` для строки, у которой идентификатор совпадает с именем из спецификации, и `X_AS` для строки с другим идентификатором:

```cpp
namespace widget
{
enum class state { idle, busy };

LUMEX_PROTOCOL_LAYOUT (status_t, (u8_<>, u16_le_<scale<std::ratio<1, 10> > >),
                       ("mode", "temperature"));

#define WIDGET_ROWS(X, X_AS)                                                  \
  X (PING, 0x01, "Проверка связи", (), (), (), (idempotent))                  \
  X (SET_RATE, 0x02, "Частота измерений",                                     \
     (u16_le_<scale<std::ratio<1, 100> > >, u8_<>), ("rate", "channel"),      \
     (status_t), (timeout (500), retries (2), accepted_in (state::idle)))     \
  X_AS (ERASE_LOG, "DELETE", 0x03, "Очистка журнала", (), (), (status_t),     \
        (dangerous))

LUMEX_PROTOCOL_DEFINE (widget_v1, my_codec, my_header, WIDGET_ROWS);
}
```

Строка: `X (идентификатор, ключ, описание, (поля...), (имена полей...), (ответ), (опции...))`; `X_AS` принимает имя из спецификации вторым аргументом. Каждая группа заключена в скобки и может содержать сколько угодно элементов с любыми запятыми внутри (`std::ratio<1, 100>`). Группа раскрывается один раз в список аргументов шаблона, поэтому ни число полей, ни число строк не ограничено: в тестах есть список из 100 строк и раскладка из 40 полей. Каждый макрос пишется с точкой с запятой после него.

Имена в таблице (`u8_`, `scale`, `timeout`, `dangerous`, `level::debug`) не требуют пространства имен: группы вычисляются внутри класса, производного от `dsl::vocabulary`. Типы и перечисления пространства имен таблицы (раскладки, состояния прибора) тоже видны.

Ключ строки: целое, символ, перечислитель или текстовая мнемоника (`"AZ"`, хранится как `dsl::text_key`).

## Что получается из строки

Для строки `SET_RATE` в протоколе `widget_v1`:

| Член | Значение |
| --- | --- |
| `widget_v1::SET_RATE_t::fields_type` | `dsl::field_list<...>`: типы полей (`::types`) и их число (`::count`) |
| `reply_type` | тип ответа или `dsl::no_reply` |
| `key ()`, `key_type` | ключ, константа |
| `options ()`, `options_type` | опции, константа (`dsl::option_set<...>`) |
| `identifier ()` | `"SET_RATE"` |
| `specification_name ()` | `"SET_RATE"`; для строки `X_AS` строка из таблицы (`"DELETE"`) |
| `description ()` | описание из таблицы |
| `field_names ()` | имена полей по порядку (`dsl::names_t`) |

Число имен полей проверяется при компиляции: строка или раскладка с другим числом имен не компилируется.

Сам протокол дает `protocol_name ()`, `framing_type`, `header_type`, `base_protocol` (`void` у корня), список команд `dsl::commands_of<P>::type` в порядке таблицы, их число `dsl::command_count<P>::value`, записи времени выполнения `dsl::command_entries<P> ()` и примесь клиента `P::lumex_methods<Client>`: метод на каждую строку с именем идентификатора (`client.SET_RATE (20, 1)`), который вызывает `Client::lumex_invoke<Row> (args...)`.

## Опции строки

| Опция | Значение |
| --- | --- |
| `timeout (ms)` | ответ должен прийти за столько миллисекунд |
| `retries (n)` | сколько раз повторить запрос после таймаута |
| `idempotent` | повтор строки ничего не меняет |
| `dangerous` | строка необратимо меняет прибор, нужно подтверждение |
| `deprecated` | строка оставлена для старых приборов |
| `stream (interval_ms)` | прибор сам присылает строку с этим интервалом |
| `accepted_in (s1, s2, ...)` | прибор принимает строку только в этих состояниях |
| `log_level (level::...)` | уровень записи лога для строки |
| `firmware (from, to)` | строка есть в версиях прошивки с `from` по `to` включительно |
| `model ("A", "B")` | строка есть только у этих моделей |

Опции хранятся как типизированные константы: `dsl::get_option<dsl::kind::timeout> (C::options ()).milliseconds`, `dsl::has_option<dsl::kind::model> (...)`, `dsl::flags_of (...) & dsl::row_flags::dangerous`. Все запросы работают в `static_assert`. Опция, указанная дважды (кроме флагов), и значение, которое не является опцией, не компилируются.

## Слои

```cpp
#define WIDGET_V2_ROWS(X, X_AS)                                               \
  X (SET_RATE, 0x12, "Частота измерений", (u16_be_<>), ("rate"), (status_t),  \
     ())                                                                      \
  X (CALIBRATE, 0x20, "Калибровка", (u8_<>), ("points"), (status_t),          \
     (dangerous))

LUMEX_PROTOCOL_EXTEND (widget_v2, widget_v1, WIDGET_V2_ROWS);
LUMEX_PROTOCOL_EXTEND_FRAMED (widget_lan, widget_v2, lan_codec, lan_header,
                              LAN_ROWS);
```

Слой (семейство, прибор, модель, диапазон прошивок) наследует базовый протокол. Строка слоя с идентификатором базы заменяет строку базы на ее месте в списке, новые строки идут после строк базы, остальные строки остаются типами базы (`widget_v2::PING_t` это `widget_v1::PING_t`). Глубина слоев не ограничена. `LUMEX_PROTOCOL_EXTEND_FRAMED` заменяет еще и кодек и заголовок (те же команды в другой кодировке).

## Записи времени выполнения

`dsl::command_entries<P> ()` возвращает по одной записи `dsl::command_entry_t` на команду в порядке списка: идентификатор, имя из спецификации, описание, ключ (`key_value_t`: целое, текст или другой тип), имена полей, наличие ответа и опции простыми значениями (`options_view_t`, состояния `accepted_in` приведены к 64-битным целым). Массив строится один раз при первом вызове.

## Макросы платформы

Идентификатор строки становится именем метода клиента без изменений. Если заголовок платформы определяет макрос с таким именем (`<windows.h>`: `DELETE`, `ERROR`, `IN`, `OUT`, `OPTIONAL`, `TRUE`, `FALSE`, `min`, `max`, `interface`, `small`; заголовки POSIX: `ECHO`, `MIN`, `MAX`, `major`, `minor`), таблица сломалась бы только в тех единицах трансляции, которые его включили. Поэтому `LUMEX_PROTOCOL_DEFINE` и `LUMEX_PROTOCOL_EXTEND` проверяют каждый идентификатор по списку таких имен на любой платформе, а строку с таким именем пишут через `X_AS`:

```cpp
X_AS (ERASE_LOG, "DELETE", 0x03, "Очистка журнала", (), (), (), ())
```

`LUMEX_PROTOCOL_CHECK_IDENTIFIERS (LIST);` проверяет список отдельно, `dsl::is_platform_macro_name ("...")` отвечает для одного имени.

## Ошибки

`error::protocol_errc` (категория `"lumex.protocol"`): `truncated` (сообщение короче своих полей), `trailing_bytes` (байты после последнего поля), `invalid_value` (значение, которое тип поля не может представить), `unknown_key` (ни одна строка протокола не имеет такого ключа). Новые коды добавляются в конец, значения существующих не меняются.

## Ограничения

- Таблицы реальных приборов не входят в библиотеку; протоколы приборов в тестах намеренно изменены по соглашению о неразглашении (NDA).
- Простое поле пишется с пустыми угловыми скобками: `u8_<>`.
- Время компиляции: список из 100 строк добавляет около 50 мс (cl.exe) и 35 мс (clang-cl) к стоимости заголовков, раскладка из 40 полей с масштабом в пределах шума (см. `benchmarks/protocol`).
