\page Transport Транспорт: байтовые потоки и транспорты сообщений

## Обзор

Модуль `lumex/applied/transport` (цель `lumex::transport`, опция `LUMEX_BUILD_TRANSPORT`) дает два вида транспорта поверх Asio:

- `stream::byte_stream` - поток байтов: последовательный порт (`serial::make_serial_stream`), TCP (`net::make_tcp_stream`), заглушка для тестов (`testing::make_mock_stream`);
- `datagram::message_transport` - транспорт целых сообщений: UDP (`net::make_udp_socket`), USB HID (`hid::make_hid_device`, с опцией `LUMEX_TRANSPORT_WITH_HID`), заглушка (`testing::make_mock_datagram`).

У каждого транспорта есть синхронный API с дедлайнами и асинхронный API для любого completion token Asio. Модуль работает начиная с C++11 и подключается одним заголовком:

```cpp
#include "lumex/applied/transport/LumexTransport"
```

Разбор кадров (SLIP, разделители, префикс длины, Modbus RTU и другие) находится в отдельном модуле `lumex/core/framing` и с транспортом не связан: кодек принимает байты, которые вернул транспорт. Если модуль `framing` собирается (`LUMEX_BUILD_FRAMING`), транспорт дополнительно дает адаптеры `framed_stream` и `framed_datagram`, которые соединяют транспорт с кодеком (раздел "Кадры").

## Сборка

| Опция | По умолчанию | Назначение |
| --- | --- | --- |
| `LUMEX_BUILD_TRANSPORT` | `ON` | Собирать модуль (требует `serial`, `expected`, `span`, `contracts`, `utility`) |
| `LUMEX_TRANSPORT_WITH_SPAWN` | `ON` | Токен `asio::yield_context` (собирает поставляемый Boost.Context) |
| `LUMEX_TRANSPORT_WITH_TESTING` | `ON` | Публичные заглушки `testing/` (`mock_stream`, `mock_datagram`) |
| `LUMEX_TRANSPORT_LOG_MIN_LEVEL` | `TRACE` | Нижний уровень лога, который вообще компилируется |
| `LUMEX_TRANSPORT_WITH_HID` | `ON`, где собирается hidapi | HID-транспорт `hid/` поверх поставляемого hidapi 0.15.0 (раздел "HID") |
| `LUMEX_HIDAPI_BACKEND` | `hidraw` | Backend hidapi в Linux: `hidraw` (нужен libudev) или `libusb` (нужен libusb-1.0) |
| `LUMEX_BUILD_FUZZERS` | `OFF` | Цели libFuzzer в `lumex/tests/fuzz` (только Clang, нужен `LUMEX_BUILD_TESTS`); короткий прогон каждой под меткой CTest `fuzz` (раздел "Фаззинг") |

У адаптеров кадров (`framed/`) опции нет: с `LUMEX_BUILD_FRAMING` транспорт собирает их, подключает `lumex::framing` и определяет `LUMEX_TRANSPORT_WITH_FRAMING=1` для себя и потребителей, как делает адаптер логгера (`LUMEX_TRANSPORT_WITH_LOGGER`). Без модуля `framing` транспорт собирается как раньше, заголовки `framed/` не ставятся и не входят в `LumexTransport`.

Библиотека всегда статическая, даже при `LUMEX_BUILD_SHARED_LIBS=ON`: каждый бинарник (EXE и каждая DLL) получает свою копию, свой `io_context` по выбору потребителя, свою категорию ошибок и свой слот лога. Asio (1.36, `ASIO_STANDALONE`, `ASIO_NO_DEPRECATED`) поставляется вместе с LumexLib и устанавливается вместе с заголовками; `LUMEX_ASIO_DIR` подставляет Asio потребителя той же версии.

## Потоки и время жизни

- Транспорт создается на executor, обычно на `stream::io_runner` (`io_context` со своими потоками).
- Все операции транспорта, а также `cancel ()` и `close ()`, выполняются на его strand; `cancel ()` и `close ()` можно вызывать из любого потока. Незавершенные операции заканчиваются с `transport_errc::cancelled`.
- Обработчик завершения никогда не вызывается внутри функции, которая начала операцию.
- Обработчики держат реализацию живой, поэтому `byte_stream` можно уничтожить в любой момент, в том числе внутри его обработчика: деструктор закрывает транспорт и сразу возвращается.

## Синхронный API

```cpp
namespace tr = lumex::applied::transport;

tr::stream::io_runner runner;                     // один поток для всех транспортов
tr::net::tcp_options_t options;
options.host = "192.0.2.10";
options.port = 4001;
tr::stream::byte_stream tcp = tr::net::make_tcp_stream (runner.get_executor (), options);

tr::status_result_t opened = tcp.open (tr::deadline_t (3000));
std::vector<std::uint8_t> reply (64);
tr::io_result_t got = tcp.read_some (tr::mutable_bytes_t (reply), tr::deadline_t (500));
if (!got.has_value () && got.error () == tr::error::transport_errc::timeout)
  ; // ответа нет, поток по-прежнему открыт
```

Синхронный вызов запускает асинхронную операцию и ждет ее. По дедлайну он отменяет операцию, дожидается ее завершения и возвращает `timeout`. Нужен поток, который выполняет executor; вызов из такого потока сразу возвращает `would_deadlock` (проверка понимает `io_context`, `thread_pool` и их strand).

## Асинхронный API

Каждая операция `async_open`, `async_read_some`, `async_write_some`, `async_write_all`, `async_receive`, `async_send` принимает любой completion token:

| Стиль | Пример | Условие |
| --- | --- | --- |
| Колбэк | `stream.async_read_some (buffer, [] (std::error_code e, std::size_t n) { ... })` | C++11 |
| `std::future` | `stream.async_open (asio::use_future).get ()` | C++11 |
| Отложенная операция | `auto op = stream.async_read_some (buffer, asio::deferred);` затем `std::move (op) (token)` | C++11 |
| Stackful-корутина | `stream.async_read_some (buffer, yield[error])` внутри `asio::spawn` | `LUMEX_TRANSPORT_WITH_SPAWN` |
| C++20-корутина | `co_await stream.async_read_some (buffer, asio::use_awaitable)` | C++20 |

Отмена отдельной операции идет через cancellation slot обработчика (`asio::bind_cancellation_slot`, `asio::cancel_after`, корутина). Сигнал `cancellation_type::terminal`, пока операция не завершена, отменяет транспорт так же, как `cancel ()`: все его незавершенные операции заканчиваются с `cancelled`, транспорт остается рабочим. Типы `partial` и `total` не поддерживаются и ничего не меняют (`cancellation_type::all` содержит `terminal`).

- **Отменяется весь транспорт.** Терминальная отмена записи завершает и цикл чтения, который параллельно идет на том же транспорте.
- Операция считается незавершенной, пока транспорт не передал ее результат обработчику. Сигнал, поданный после этого, ни на что не влияет, даже если обработчик еще ждет своей очереди на своем executor. Сигнал, поданный раньше, отменяет остальные незавершенные операции транспорта, даже если до strand он дошел позже, если только обработчик к этому времени еще не выполнен (сама операция может завершиться со своим результатом). Слот остается таким, каким его оставляют операции самой Asio.
- Как и для объектов самой Asio, сигнал подается на executor обработчика, а не одновременно с завершением операции.
- Таймер `asio::cancel_after` выполняется на strand транспорта. Обработчик, привязанный к голому executor многопоточного `io_runner` (или корутина, запущенная на нем), выполнялся бы рядом с этим таймером, чего `cancel_after` в Asio не допускает: такой обработчик нужно привязать к strand (`asio::bind_executor (asio::make_strand (runner.get_executor ()), handler)`).
- Открытие последовательного порта не прерывается ни `cancel ()`, ни терминальной отменой: оно заканчивается вместе с ограниченным открытием, самое позднее через `open_deadline`.

Транспорт не держит работу (outstanding work) на executor обработчика: обработчик, который держит своего владельца и хранится в незавершенной операции, держал бы эту работу вечно, и деструктор его `io_context` не вернулся бы. Поэтому контекст, который выполняет только обработчики (`asio::bind_executor (ui, ...)`), может остаться без работы и выйти из `run ()` раньше обработчика. Если `run ()` не должен возвращаться раньше обработчика, держите на этом контексте `executor_work_guard`, пока операция не завершена. Executor обработчика должен жить, пока обработчик не выполнен или не уничтожен, поэтому его контекст объявляется раньше `io_runner` и уничтожается после него:

```cpp
asio::io_context ui;                 // контекст обработчиков: объявлен первым,
tr::stream::io_runner runner;        // поэтому runner и его незавершенные операции
                                     // уничтожаются раньше ui
tr::stream::byte_stream stream = make_stream (runner.get_executor ());

auto guard = asio::make_work_guard (ui);  // run () ждет обработчик
stream.async_read_some (buffer, asio::bind_executor (ui,
    [&guard] (std::error_code error, std::size_t bytes)
      {
        guard.reset ();                    // работы больше нет
        // ...
      }));
ui.run ();

// Неправильно: io_runner runner; asio::io_context ui; (ui уничтожается первым,
// а завершившаяся в runner операция отправила бы обработчик в уничтоженный ui).
```

## Ошибки

`error::transport_errc`: `timeout`, `cancelled`, `closed`, `not_open`, `disconnected`, `would_deadlock`, `invalid_endpoint`, `report_too_large`, `bad_report_descriptor`, `permission_denied`, `unknown_report_id`. Ошибки операционной системы приходят без изменений в `std::system_category`, с одним исключением: отказ в доступе при открытии последовательного порта в POSIX (`EACCES`, `EPERM`) становится `permission_denied` (см. раздел о правах доступа). В Windows `ERROR_ACCESS_DENIED` при открытии COM-порта обычно значит, что порт занят, поэтому остается системной ошибкой. Собственные категории Asio никогда не выходят наружу: `operation_aborted` превращается в `cancelled`, `eof` и сброс TCP-соединения в `disconnected`, ошибка разрешения имени в `invalid_endpoint`.

Значения с переносимым смыслом сравниваются и со стандартными условиями: `timeout` равен `std::errc::timed_out`, `cancelled` равен `std::errc::operation_canceled`, `permission_denied` равен `std::errc::permission_denied`. У остальных значений такого соответствия нет.

Категория `transport_errc` своя в каждом бинарнике (библиотека статическая), поэтому код ошибки, полученный из другой DLL, сравнивайте через `error::is_transport_error (code, transport_errc::disconnected)`: эта функция сравнивает и по имени категории `"lumex.transport"`.

## Лог

Записи (`log::log_record_t`: уровень, компонент `transport.serial` / `transport.tcp` / `transport.udp` / `transport.hid`, экземпляр, текст, байты) уходят в слот этого бинарника. По умолчанию записи от `warning` и выше печатаются в `std::cerr`. Потребитель ставит свой приемник через `log::set_log_sink`, меняет порог `log::set_log_level` во время работы и ограничивает компоненты `log::set_component_filter`. Байты показываются через `log::format_dump` (hex и текст с именами управляющих байтов, по умолчанию не больше 256 байт). На уровне `trace` пишется каждый принятый и отправленный кусок.

С модулем `logger` (`LUMEX_BUILD_LOGGER`, тогда определен `LUMEX_TRANSPORT_WITH_LOGGER`) лог транспорта можно направить в файл `LumexLogger`:

- `log::install_lumex_logger_sink ()` делает `LumexLogger` приемником этого бинарника и подключает порог транспорта к уровню логгера: при каждом перечитывании файла-триггера (`enable_logs`) порог меняется вместе с ним, а пока логгер выключен, порог `off`. Возвращает `false`, если все 8 мест для функций уведомления логгера заняты другими бинарниками: тогда порог выставляется один раз.
- `log::uninstall_lumex_logger_sink ()` возвращает приемник по умолчанию.
- Программа, которая пишет в лог только через транспорт, сама файл-триггер не проверяет (пока логгер выключен, вызовов логгера нет). Ей нужен `trigger_file_watcher` логгера или `log::lumex_logger_watch_timer` (таймер на `io_runner`, уничтожается раньше него).

## Статистика

`byte_stream::statistics ()` и `message_transport::statistics ()` возвращают снимок `statistics::statistics_t`: байты и операции в обе стороны (для транспорта сообщений: сообщения), удачные открытия, ошибки по значениям `transport_errc` и прочие ошибки, тайм-ауты, отмены, время последней активности. Счетчики атомарные и считаются в базовых классах, поэтому последовательный порт, TCP, UDP и заглушки считают одинаково. Дедлайн синхронного вызова считается один раз, как тайм-аут. `reset_statistics ()` обнуляет счетчики; сброс во время обмена приблизительный, снимок читает счетчики по одному.

## Права доступа (Linux)

Если ОС отказывает в открытии узла последовательного порта или HID-устройства (`/dev/hidrawN`; `EACCES` / `EPERM`), открытие завершается `permission_denied`, а в лог (уровень `error`) пишется узел, его владелец, группа, режим и способ исправить. Справка строится на рабочем потоке открытия и только при включенном логе ошибок, поток ввода-вывода не обращается к базе пользователей. Шаблоны правил udev для доступа без root ставятся в `share/LumexLib/udev` (`99-lumex-serial.rules` по группе и VID `16e0`, `70-lumex-uaccess.rules` для пользователя за консолью); как их установить, описано в `README.md` рядом с ними.

## Сессии и переподключение

`session::stream_session` и `session::message_session` держат открытым один транспорт, который делает фабрика: открывают его, замечают потерю связи и открывают новый. Это транспортный уровень переподключения; повтор `identify ()` и повторную отправку данных после переподключения решает клиент протокола (фазы 4 и 5).

```cpp
namespace ss = tr::session;

ss::serial_selector_t selector;                   // порт по USB-адаптеру, а не по имени
selector.vid = "16E0";
selector.serial_number = "B71946KX";
selector.settings.baud_rate = 115200;

ss::session_options_t options;
options.name = "device";
options.policy.max_attempts = 0;                  // пытаться без ограничения
ss::stream_session link (runner.get_executor (), ss::make_serial_factory (selector), options);

ss::device_watcher watcher (runner.get_executor ());   // опрос портов раз в секунду
watcher.watch_presence (selector, link.presence_sink ());

link.open (tr::deadline_t (5000));
link.async_read_some (buffer, handler);           // потеря связи запускает переподключение
```

- **Состояния** `channel_state`: `closed` до `start ()`, `connecting` в попытках первого открытия, `open`, `reconnecting` после потери связи, `faulted`, когда цикл исчерпал `max_attempts` (`start ()` начинает новый цикл). `close ()` из любого состояния возвращает `closed`. `state_snapshot ()` читает состояние вместе с номером изменения, `async_wait_state_change` от снимка не пропускает изменений; `on_state_change` вызывается на strand сессии при каждом изменении.
- **Повторы** `reconnect_policy_t`: первая попытка цикла сразу, затем ожидание `initial_delay * multiplier^(n - 1)`, не больше `max_delay`, с разбросом `jitter`; между двумя попытками не меньше 1 мс. Связь, которая не продержалась `initial_delay`, не дает переподключаться подряд: без переданных данных это неудачная попытка того же цикла, с данными новый цикл, первая попытка которого ждет. Попытка открытия ограничена `open_timeout`.
- **Потеря связи** видна по вводу-выводу самой сессии: ошибка, которую принимает `is_link_lost` (все, кроме `cancelled`, `timeout`, `would_deadlock`, `report_too_large`), запускает переподключение до вызова обработчика. Тихую потерю у сессии, которая ничего не читает, сообщает только присутствие устройства: `set_device_present (false)` (его вызывает `device_watcher` через `presence_sink ()`) останавливает попытки, `set_device_present (true)` сразу делает следующую. Операция, начатая, пока сессия не открыта, завершается с `not_open`; ничего не отправляется повторно.
- **Селекторы** делают фабрики: `make_serial_factory` по пути или по VID, PID и серийному номеру адаптера (порт ищется при каждом открытии, поэтому `COM7`, вернувшийся как `COM9`, находится снова; путь `/dev/serial/by-id/...` сравнивается через `realpath`), `make_tcp_factory`, `make_udp_factory`, а для HID `hid::make_hid_factory` (раздел "HID", "Селекторы и наблюдатель"). Перечисление портов селекторов и `device_watcher` не открывает порты (`enumerate_serial_ports_without_probe`), чтобы не дергать линии модема приборов и не мешать открытию сессии.
- **`close ()` и `cancel ()`** сразу заканчивают подключение и переподключение и завершают ожидающие `async_open` и `async_wait_state_change` с `cancelled`. `close ()` закрывает транспорт; `cancel ()` открытой сессии отменяет ее ввод-вывод и оставляет связь.
- **Отмена отдельной операции** работает как у транспортов. Терминальный сигнал на слоте `async_open` или `async_wait_state_change` делает то же, что `cancel ()`; на слоте операции ввода-вывода он отменяет незавершенные операции текущего транспорта, связь остается. `partial` и `total` ничего не меняют. Начальные функции сообщают strand сессии, поэтому таймер `asio::cancel_after` выполняется на нем. Работу на executor обработчика сессия не держит (см. асинхронный API).
- **Время жизни.** Сессию можно уничтожить в любой момент, в том числе в ее колбэке состояния или обработчике: деструктор закрывает асинхронно и возвращается, колбэк состояния после него не вызывается. Уничтожайте сессию раньше `io_context` ее executor.
- **Счетчики:** `statistics ()` возвращает счетчики транспорта последней попытки, `session_statistics ()` попытки, неудачные попытки и переподключения.

## Кадры

`framed::framed_stream<Codec>` и `framed::framed_datagram<Codec>` (только с модулем `framing`) соединяют транспорт с кодеком `core/framing`: читают кадры целиком, пишут полезный груз как кадр. Заголовки входят в `LumexTransport`, пространство имен `lumex::applied::transport::framed`.

```cpp
namespace fr = lumex::core::framing;

tr::stream::byte_stream stream = tr::net::make_tcp_stream (runner.get_executor (), options);
stream.open (tr::deadline_t (2000));

framed::framed_options_t limits;
limits.queue_bound = 32;                           // кадров в очереди
framed::framed_stream<fr::slip::slip_codec> link (std::move (stream), fr::slip::slip_codec (), limits);

link.write_frame (payload, tr::deadline_t (500));   // синхронно, с дедлайном
link.async_read_frame ([] (std::error_code error, framed::frame_t frame) { /* ... */ });
framed::frame_result_t reply = link.read_frame (tr::deadline_t (500));
```

- **Владение.** Адаптер владеет транспортом, который в него переложили (`std::move`), и закрывает его в деструкторе. Транспорт доступен через `transport ()`: открыть его, взять имя и счетчики можно там; читать из него или писать в него в обход адаптера нельзя, декодер забрал бы байты. Кодек перекладывается в адаптер и работает только на его strand.
- **Чтение.** Первый `read_frame` / `async_read_frame` (или `start ()`) запускает декодер: он непрерывно читает транспорт кусками (`read_chunk_size`), кормит кодек на strand транспорта, а готовые кадры отдает ожидающему читателю или кладет в очередь на `queue_bound` кадров. Кадры не теряются между двумя чтениями, пока в очереди есть место. Читателей может быть несколько, они получают кадры по порядку. Ошибка самого транспорта (`disconnected`, `not_open`, ...) останавливает декодер, завершает ожидающих читателей и сбрасывает неполный кадр кодека (заново открытый транспорт начинает новый кадр); следующее чтение запускает декодер снова. Декодер держит чтение на транспорте с первого чтения до `close ()`: у настоящего транспорта (последовательный порт, TCP, UDP) это работа Asio на его `io_context`, поэтому `io_context::run ()` не возвращается, пока адаптер открыт, даже после последнего обработчика. Закончите работу `close ()` (или уничтожьте адаптер) либо ограничьте запуск (`run_for`, `stop`); заглушки такой работы не держат.
- **Переполнение очереди.** Если очередь полна, самый старый кадр отбрасывается: читатель, который отстает от прибора, видит свежие кадры. Каждый отброшенный кадр считается в `dropped_frames`, а в лог (`warning`, компонент `transport.framed.stream` или `transport.framed.datagram`) пишется одна запись на серию отбрасываний; серия кончается, когда читатель разобрал очередь до половины границы.
- **Ошибки кадрирования** (`bad_checksum`, `frame_too_large`, `truncated`, `bad_header`, `bad_escape`) считаются по значениям `framing_errc` (`statistics ().errors_of (...)`) и пишутся в лог (одно предупреждение на серию ошибок подряд, остальные на уровне `debug`), но читателю не передаются: декодер сам ищет границу следующего кадра, а ошибка чтения означала бы для вызывающего то же, что отказ транспорта. Читатель ждет следующий хороший кадр; прибору, которому нужен повтор, достаточно тайм-аута и счетчика.
- **Запись.** Кадр кодируется кодеком на strand и пишется целиком (`write_all`). Полезный груз, который кодек не принимает, завершает запись с `framing_errc::payload_too_large` без записи в транспорт. Записи идут одна за другой в порядке начала, кадры не перемешиваются. Область памяти полезного груза должна жить до вызова обработчика.
- **`framed_datagram`.** Кодек применяется к каждой датаграмме отдельно, из начального состояния: хвост неполного кадра не достраивается следующей датаграммой, потерянная датаграмма не портит соседние. В датаграмме может быть несколько кадров. Кадр приходит как `datagram::message_t` с `report_id` датаграммы; `write_frame (report_id, payload, deadline)` задает `report_id` отправки. Датаграмма без единого полного кадра считается как `truncated` (кодек не сообщает о неполном кадре после полного), пустая датаграмма игнорируется.
- **Те же правила, что у транспортов.** Любой completion token (колбэк, `use_future`, `deferred`, `yield_context`, `use_awaitable`); начальные функции сообщают strand транспорта; обработчик никогда не вызывается внутри начавшей операцию функции и выполняется на своем executor; работу на нем адаптер не держит; `cancel ()` и `close ()` из любого потока; синхронный вызов по дедлайну отменяет адаптер и возвращает `timeout` (считается в `timeouts`), на потоке executor возвращает `would_deadlock` (не считается). Терминальная отмена на слоте обработчика чтения или записи делает то же, что `cancel ()`: заканчиваются с `cancelled` все чтения и записи адаптера, а декодер продолжает работу; сигнал после выдачи результата ничего не отменяет. `close ()` закрывает транспорт, забывает очередь и неполный кадр кодека. Адаптер можно уничтожить в любой момент, в том числе в его обработчике: деструктор закрывает асинхронно и возвращается, ожидающие обработчики завершаются с `cancelled`.
- **Счетчики.** `statistics ()` возвращает `framed_statistics_t`: кадры и байты в обе стороны (байты считаются вместе с обрамлением), `dropped_frames`, ошибки по значениям `framing_errc`, прочие ошибки и `timeouts` синхронных вызовов; `transport_statistics ()` отдает счетчики транспорта под адаптером; `reset_statistics ()` обнуляет оба набора; `queued_frames ()` показывает длину очереди.

## Транспорты

- **Последовательный порт.** Открытие ограничено дедлайном `open_deadline` (рабочий поток с `CancelSynchronousIo` в Windows, `O_NONBLOCK` в POSIX), поэтому отсутствующий Bluetooth-порт не подвешивает вызов. Настройки `serial_settings_t` (скорость, биты данных, четность, стоповые биты, управление потоком); значение, которое платформа не умеет (четность mark/space, 1,5 стоповых бита вне Windows), дает `std::errc::not_supported`.
- **TCP.** Разрешение имени и подключение; `no_delay` (по умолчанию включен) и `keep_alive`. Отмена или закрытие во время открытия завершают его сразу, даже если имя еще разрешается.
- **UDP.** Сокет, подключенный к одному адресату: один прием возвращает одну датаграмму, одна отправка пишет одну. Датаграмма длиннее `max_datagram_size` обрезается до этого размера на всех платформах (с предупреждением в логе). Отправка сообщения с ненулевым `report_id` дает `std::errc::invalid_argument`.

## HID

`hid::make_hid_device (executor, hid_options_t)` (опция `LUMEX_TRANSPORT_WITH_HID`, заголовок `hid/LumexHidDevice.hpp`, входит в `LumexTransport`) дает USB HID-устройство как `datagram::message_transport` (`hid::hid_device`) поверх поставляемого hidapi 0.15.0: одно сообщение - один отчет.

```cpp
namespace hid = tr::hid;

hid::hid_runtime runtime;                    // в main: потоки HID присоединяются до выхода из main
hid::hid_options_t options;
options.vendor_id = 0x1234;                  // или options.path из enumerate_hid_devices
options.product_id = 0x5678;
hid::hid_device device = hid::make_hid_device (runner.get_executor (), options);
device.open (tr::deadline_t (2000));

tr::datagram::message_t request;
request.report_id = 1;                       // выходной отчет 1; 0 у устройства без номеров
request.payload = { 0x01, 0x02 };            // дополняется нулями до размера отчета
device.send (request, tr::deadline_t (500));
tr::datagram::message_result_t reply = device.receive (tr::deadline_t (500));
```

- **Поиск.** `hid::enumerate_hid_devices (hid_filter_t)` перечисляет устройства по VID, PID, серийному номеру и пути (пустое или нулевое поле подходит всем) и не открывает их для работы, поэтому в списке есть и устройства без прав доступа. В Windows hidapi при перечислении открывает каждый интерфейс с нулевым доступом, чтобы прочитать атрибуты и строки, а само перечисление идет под тем же мьютексом процесса, что и `hid_open_path`, поэтому вызов может ждать медленное открытие другого устройства. В Linux и macOS hidapi дает по записи на каждую верхнеуровневую usage, все с одним путем. `hid_options_t::path` открывает конкретный путь; без пути открывается первое устройство, подходящее по VID, PID и серийному номеру, а если такого нет, открытие завершается с `std::errc::no_such_device`.
- **Дескриптор и номер отчета.** При открытии транспорт читает report descriptor (`hid_get_report_descriptor`) и разбирает его (`hid::analyze_report_descriptor`, перенос `AnalyzeHidReportDescriptor` из DChannel с размерами по номерам отчетов): нумерует ли устройство отчеты и каков размер каждого входного и выходного отчета. Дескриптор, который нельзя прочитать или разобрать, дает `bad_report_descriptor`; номер отчета никогда не угадывается. Разбор строже, чем в DChannel: в дескрипторе с номерами отчет до первого `Report ID`, а также `Report ID` 0, `Pop` без `Push` и отчет больше 64 КиБ дают `bad_report_descriptor`. `message_t::report_id` явный в обе стороны: принятый отчет нумерующего устройства несет свой номер, отчет устройства без номеров приходит с 0; отправка называет выходной отчет, который у устройства есть, иначе `unknown_report_id` (у устройства без номеров есть только отчет 0). `hid::opened_report_layout (device)` показывает разбор открытого устройства.
- **Селекторы и наблюдатель.** `hid::hid_selector_t` называет устройство тем, что оно есть, а не где оно: VID, PID, серийный номер (без учета регистра), номер интерфейса USB, usage page и usage верхней коллекции или путь (с путем остальное не смотрится). Нулевое или пустое поле подходит всем, селектор без полей не подходит никому, как и у последовательного. hidapi перечисляет по записи на интерфейс и коллекцию, поэтому интерфейс и usage page отличают части составного устройства. `hid::make_hid_factory (selector)` дает фабрику для `message_session`: устройство ищется при каждом открытии в рабочем потоке открытия (`hid_options_t::resolve_path`), сама фабрика ничего не перечисляет, а устройство, вернувшееся под другим путем, находится снова; если ничего не подошло, открытие завершается с `invalid_endpoint` (неудачная попытка, сессия повторяет по политике). `device_watcher` принимает HID-селекторы теми же `watch` и `watch_presence` (события `hid_device_event_t`). Устройство - это путь: несколько записей с одним путем (по usage) дают одно появление и один уход, в событии первая подошедшая запись, поэтому потребитель, открывающий устройство по появлению, открывает его один раз; внутри одного опроса уходы идут раньше появлений. Перечисление последовательных портов выполняется в каждом опросе, перечисление HID (`hid::default_hid_enumeration`) в том же опросе и только пока наблюдается хотя бы один HID-селектор; оно идет на strand наблюдателя и может ждать медленное открытие устройства (мьютекс hidapi). Сбой одного перечисления пропускает опрос только своих селекторов, `polls ()` считает опрос, если хотя бы одно перечисление вернулось. Перегрузки `watch` для HID есть только при `LUMEX_TRANSPORT_WITH_HID` (селектор живет в `hid/`, которая без HID не собирается и не ставится); конструктор и сам класс от опции не зависят. Устройство, вернувшееся под другим путем, - это уход старого пути и приход нового.

```cpp
hid::hid_selector_t selector;
selector.vendor_id = 0x1234;                 // синтетические ID
selector.product_id = 0x5678;
selector.usage_page = 0xFF00;                // нужная коллекция составного устройства

ss::message_session link (runner.get_executor (), hid::make_hid_factory (selector), options);
ss::device_watcher watcher (runner.get_executor ());   // опрос раз в секунду
watcher.watch_presence (selector, link.presence_sink ());
watcher.watch (selector, [] (ss::hid_device_event_t const &event) { /* arrived / removed */ });
```

- **Размеры.** Отправляемый отчет дополняется нулями до размера своего выходного отчета; полезный груз длиннее отчета дает `report_too_large`, и ничего не отправляется. Принятый `payload` - отчет без номера в том виде, в каком его прислало устройство.
- **Потоки.** hidapi блокирует, поэтому у каждого открытого устройства есть поток чтения: он вызывает `hid_read_timeout` порциями по `read_slice` (100 мс) и передает каждый отчет на strand. Флаг остановки проверяется до и после каждой порции: `close ()` останавливает поток не позже чем через одну порцию, а отчет, пришедший после остановки, отбрасывается. Дескриптор hidapi закрывает только поток чтения после своего последнего чтения. Открытие и записи выполняются на небольшом блокирующем исполнителе (не больше двух потоков), по одной записи устройства за раз, поэтому strand никогда не блокируется. Запись, которая ждет свободный поток, завершается по дедлайну синхронного вызова или `cancel ()` с `cancelled` и до hidapi не доходит; запись, застрявшая внутри hidapi (драйвер не отвечает), занимает поток, и открытия и записи других устройств ждут за ней. Пока прием не ждет, отчеты копятся в очереди на `max_queued_reports` (256); при переполнении самый старый отбрасывается с предупреждением в логе.
- **`hid_runtime`.** Потоки принадлежат общему для модуля `hid_runtime`. Каждое открытое устройство держит на нем ссылку, а поток обслуживания присоединяет закончившиеся потоки чтения, поэтому поток никогда не ждет сам себя: устройство, последняя ссылка на которое исчезла в его же потоке чтения, только ставит флаг остановки. `hid_runtime::shutdown (deadline)` закрывает все устройства и присоединяет все потоки; возвращает `false`, если дедлайн прошел раньше (например, запись застряла в драйвере) или вызов сделан из потока самого `hid_runtime`. Вызовы из нескольких потоков (например, явный `shutdown` и деструктор объекта-владельца) выполняются по очереди, второй ждет первый в пределах своего дедлайна. Счетчик `stats ().open_devices` уменьшается, когда strand устройства выполнит закрытие, поэтому сразу после `shutdown` он может отставать. Объект-владелец `hid_runtime runtime;` в `main` делает то же при выходе из `main`, даже если устройство еще открыто. Без него при выходе из процесса оставшиеся потоки чтения получают флаг остановки во время статической деинициализации, после деструкторов статических объектов, созданных позже первого обращения к HID, и не присоединяются (после флага вызовов hidapi нет, потоки завершает ОС). Поэтому `io_runner` потребителя должен пережить открытые устройства, иначе программа вызывает `shutdown` раньше. `hid_exit` не вызывается никогда: в процессе может быть копия hidapi из DChannel.
- **Отмена и ошибки.** Как у остальных транспортов: любой completion token, `cancel ()` и `close ()` из любого потока, отмена через слот обработчика, счетчики `statistics ()` (байты полезного груза без номера и дополнения). Запись, которая уже ушла в hidapi, завершается своим результатом (hidapi ее не отменяет), запись в очереди завершается с `cancelled`. Неудачное чтение останавливает поток чтения: ожидающий и все следующие приемы завершаются с `disconnected` до закрытия и нового открытия.
- **Linux.** По умолчанию backend hidraw (нужен libudev, пакет `libudev-dev`); `LUMEX_HIDAPI_BACKEND=libusb` выбирает libusb-1.0. Если библиотека backend не найдена, `LUMEX_TRANSPORT_WITH_HID` по умолчанию выключена, а явное `ON` дает понятную ошибку конфигурации. Проверка hidraw на настоящих устройствах (с номерами отчетов и без них) еще не проведена.

## Соответствие DChannel

Модуль закрывает транспортную часть DChannel. Код продуктов на него пока не переводится; таблица показывает, чем заменить каждую часть при переходе.

| DChannel | LumexLib |
| --- | --- |
| `DCT_SERIAL_PORT`, `DCT_SERIAL_PORT_SYNC`, `Create`, `CreateSerialPort` | `serial::make_serial_stream` и `serial_stream_options_t` (оба режима DChannel дает один поток: синхронный и асинхронный API) |
| `DCT_NET_TCP` | `net::make_tcp_stream` |
| `DCT_NET_UDP` | `net::make_udp_socket` |
| `DCT_USB_HID`, `SelectDevice`, `EnumerateDevices`, `GetNextDeviceName`, `GetNextSerialNumber` | `hid::make_hid_device` (`hid_device`) и `hid_options_t` (путь или VID, PID, серийный номер); `hid::enumerate_hid_devices`; выбор устройства: `hid::hid_selector_t` (VID, PID, серийный номер, интерфейс, usage page) и `hid::make_hid_factory` для сессии, появление и уход: `device_watcher` с HID-селектором; последовательные порты перечисляет `applied/serial` |
| `DCT_NAMED_PIPE_SERVER`, `DCT_NAMED_PIPE_CLIENT` | не переносятся |
| `DCP_SIMPLE` | `byte_stream` без кодека |
| `DCP_ASCII`, `SetFrameDelimiters` | `core/framing`: `delimiter_codec` |
| `DCP_SLIP` | `core/framing`: `slip_codec` |
| `DCP_TCP` (длина в первом байте) | `core/framing`: `length_prefix_codec` с `width = 1` |
| `DCP_HID_1` | `hid_device` (номер отчета явно в `message_t::report_id`, размеры из report descriptor) и кодек потребителя для заголовка прибора |
| `DCP_COM7BIT`, `DCP_TRANSPORT`, `DCP_UDP` | не переносятся (см. ниже) |
| `IsOpened`, `IsConnected` | `is_open ()`; потеря связи приходит ошибкой `disconnected` |
| `Read`, `Write` | `read_some`, `write_some`, `write_all` с дедлайном |
| `StartDataExchange`, `GetReceivedData`, `SendData` | `framed_stream` / `framed_datagram`: `start ()`, `read_frame`, `write_frame` |
| `StopDataExchange`, `Close`, `Delete` | `close ()` из любого потока; блокирующее чтение завершается сразу с `cancelled` |
| `SetNotification` (окно, сообщение, событие) | completion token: колбэк, future, корутина |
| `GetChannelStatistic` | `statistics ()` транспорта и `framed_stream::statistics ()` (кадры, ошибки кадрирования, отброшенные кадры) |
| Файл-триггер логгера | `log::install_lumex_logger_sink ()`: лог транспорта в `LumexLogger`, порог следует за перечитыванием файла-триггера |

Сознательно не входят в библиотеку протоколы конкретных устройств: 7-битная кодировка последовательного порта, транспортный протокол с номерами пакетов, подтверждениями и повторами, заголовок `[ReportID][Size]` HID-отчетов прибора и заголовок старого UDP-протокола приборов (длина, атрибут, номер пакета). Это форматы приборов, а не транспорта; при переходе их реализует код прибора поверх `byte_stream` или `message_transport` и, где удобно, стадий `core/framing`.

## Примеры

- `lumex/examples/transport/example_transport_sync.cpp`: синхронный обмен с эхо-сервером по TCP (или с последовательным портом, имя которого передано аргументом) и приемник лога.
- `lumex/examples/transport/example_transport_async.cpp`: цепочка колбэков и закрытие потока из другого потока во время чтения.
- `lumex/examples/transport/example_transport_framed.cpp`: `framed_stream` с кодеками SLIP и строк (`delimiter_codec`) поверх TCP с эхо-сервером на loopback; печатает кадры и счетчики кадрирования. Запускается без оборудования.
- `lumex/examples/transport/example_transport_hid.cpp`: без аргумента перечисляет HID-интерфейсы машины и завершается с 0, даже если их нет; с `--count` печатает только их число (так его запускает CTest, чтобы строки устройств машины не попадали в лог); с аргументом `VVVV:PPPP[:serial]` (шестнадцатеричные) или путем открывает устройство через `hid_selector_t` и печатает раскладку отчетов из разбора дескриптора.

Все примеры зарегистрированы в CTest (`examples.transport.*`) и запускаются без оборудования.

## Фаззинг

С `LUMEX_BUILD_FUZZERS=ON` (Clang, `LUMEX_BUILD_TESTS`) собирается цель libFuzzer разбора дескриптора HID: `fuzz.transport.hid_descriptor` (`lumex/tests/fuzz/transport/`). Каждый вход - дескриптор; разбор не должен читать за его концом (AddressSanitizer) и обязан либо вернуть `bad_report_descriptor`, либо согласованную раскладку (номера отчетов строго по возрастанию, не больше 64 КиБ на отчет, функции `input_size`, `output_size`, `has_output`, `max_input_size` согласуются со списками, повторный разбор дает то же). Начальный корпус цель пишет сама из синтетических дескрипторов и их испорченных вариантов. CTest запускает ее на 30 секунд под меткой `fuzz` (`ctest -L fuzz`); найденное становится регрессионным тестом набора `transport.hid`.
