# expected benchmarks

The `expected` of this library (`lumex::core::expected::result::expected`) against `std::expected` of the standard library in use (libstdc++ 13.2 or libc++ of Clang 23.1, C++23) and `boost::outcome_v2::result` of Boost.Outcome 1.92, on the same scenarios and the same source. The `expected` of this library is measured at C++11, C++14, C++17, C++20 and C++23 (the storage layers and the `constexpr` and `requires` branches differ between the standards, so the layers are compared with each other too); `std::expected` at C++23; Outcome at C++17. Two toolchains were measured, each with its own standard library: GCC 13.2 with libstdc++ and Clang 23.1.0 with libc++; nothing here says how MSVC compiles the same code.

## What is compared

| Alternative | Measured | Notes |
| --- | --- | --- |
| `std::expected` (libstdc++ 13.2.0 with GCC, libc++ with Clang 23.1) | yes, C++23, the baseline | the only standard facility; C++23 |
| `boost::outcome_v2::result` (Boost.Outcome 1.92.0, headers only, `/opt/boost-1.92.0`) | yes, C++17 | `result<T, E, policy::terminate>`; no monadic members, no `value_or`, no `operator*` (`assume_value ()` stands for it); refuses a result whose value and error type are the same type, so the error of the "int" scenarios is `unsigned` and of the "string" scenarios a struct that holds a string, on every side; the default constructor of `result<void, E>` is deleted |
| `tl::expected` | no | not installed on this machine (a search for `expected.hpp` found only libstdc++'s `<expected>`); nothing was vendored |
| `boost::leaf`, `outcome::outcome` and the rest of Boost.Outcome | no | different designs (`leaf` is an error-handling framework, not a result type) |

## Method

- One source, `bench_expected.cpp`, compiled once per implementation and standard with `-DBENCH_EXPECTED_IMPL=1|2|3` (`bench_expected_impl.hpp` maps it to the type under test and defines `ok<X> (...)`, `err<X> (...)`, `ok_void<X> ()` and `deref (x)`). Every variant is built with the flags of the Release profile of the library, whose effective optimization is `-O2 -g -DNDEBUG -fomit-frame-pointer -march=x86-64 -mtune=generic` (the profile also adds the warning flags of the library; the benchmark builds without warnings, and also with `-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Wshadow -Wold-style-cast` on C++11, 14, 17, 20 and 23). There are no sanitizers. `LUMEX_ASSERT` is active as in every build of the library (it aborts in every build, `NDEBUG` included).
- Scenarios (the unit of an operation is in the description column of the results): construction in place from a value or an error and destruction; copy; construction plus move construction; copy assignment of the same alternative and of the other alternative; `value ()`, `operator*`, `error ()`, `has_value ()` over an array of 1 024 (all values, all errors, one error in eight in a fixed pseudo-random order) and the usual `if (has_value ()) *x else x.error ()`; `value_or`; `transform`, `and_then`, `or_else` and the three in a row; four nested `noinline` calls that return the result by value. Types: `<int, unsigned>`, `<std::string, unsigned>` with 12 characters (no allocation) and with 64 (an allocation), `<int, std::string>`, `<std::string, text_error_t>`, `<std::array<int, 16>, unsigned>` (64-byte value).
- `sizeof`, `alignof` and the properties trivially copyable, trivially destructible, standard layout and nothrow move constructible of 16 types are written to `sizes.csv` by every executable.
- Equal work: every scenario returns a checksum of what it computed from the same inputs; `run_benchmark.py` compares the checksums of all executables and stops when two of them differ. The optimizer is kept from deleting or hoisting the work with empty `asm` statements that read the objects built in the loops (and clobber memory) and with inputs (values, pointers, sizes) that pass through `asm`. The arrays are built at run time. Not covered by this check: the generated code can still differ in what it keeps in registers; the asm statements only prevent removal.
- A scenario is calibrated until one run lasts at least 20 ms, runs once as warm-up and 15 times for the numbers. `run_benchmark.py` runs every executable `--passes` times (default 5), one pass over all executables after the other, and keeps the median of the pass medians as the time, the smallest and the largest pass median as the spread between processes, and the smallest minimum and largest maximum of the repetitions. A dagger in the tables marks a time whose largest pass median is more than 25 % above the smallest; the spread over all scenarios is a median of 1.02 (largest 1.28), so a difference below 10 % is not a result.
- The process is pinned to one CPU (CPU 4, a performance core) with `taskset`; the whole run is done under the build lock of the machine, so nothing else compiles or tests meanwhile.
- Compile time: `compile_time.cpp` includes the header and uses the common API for three types; `run_benchmark.py --compile-time` measures the wall time of `-fsyntax-only -O0` and of `-c -O2` of that unit (median of 7), next to the same unit without the header (`no header`), which is only measured at C++11 and C++23.

## Running

```sh
cmake -S . -B build-bench -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++ \
      -DLUMEX_BUILD_BENCHMARKS=ON \
      -DLUMEX_BENCH_BOOST_INCLUDE_DIR=/opt/boost-1.92.0/include
cmake --build build-bench --target LumexExpectedBench_lumex_cxx11 LumexExpectedBench_lumex_cxx14 \
      LumexExpectedBench_lumex_cxx17 LumexExpectedBench_lumex_cxx20 LumexExpectedBench_lumex_cxx23 \
      LumexExpectedBench_std_cxx23 LumexExpectedBench_outcome_cxx17
python benchmarks/expected/run_benchmark.py --build-dir gcc=build-bench --passes 5 --cpu 4 \
       --compile-time --compiler "gcc=g++" --boost-include /opt/boost-1.92.0/include
```

The same in a second build tree with `-DCMAKE_CXX_COMPILER=clang++` (Clang takes libc++ by default). The Clang rows of the committed results come from `run_benchmark.py --build-dir clang=build-bench-clang --passes 5 --cpu 4` and were added to the GCC rows by `run_benchmark.py --merge gcc/expected_benchmark.csv clang/expected_benchmark.csv --out-dir results`. The Clang compile times were measured with `run_benchmark.py --compile-time-only --compiler "clang=clang++ -stdlib=libc++" --cpu 3 --compile-repeats 7 --out-dir clang`; `--merge` also combines the `compile_time.csv` files that lie next to the CSV files it is given.

`run_benchmark.py` writes `results/expected_benchmark.csv`, `results/sizes.csv`, `results/compile_time.csv` and, through `plot_results.py` (Python standard library only), the Markdown tables and the SVG charts. The target `LumexExpectedBenchmarkRun` runs the executables of one build tree and writes into that build tree, so it never overwrites the committed results. Boost is optional: without `boost/outcome/result.hpp` the Outcome variant is skipped with a message. The runs took about 30 minutes with 5 passes.

## Results

Measured on an Intel Core i7-12700K (Linux 6.1, pinned to CPU 4, frequency governor `powersave` of `intel_pstate`), GCC 13.2.0 with libstdc++, Boost 1.92.0 (headers only), 5 passes, October 2026. The full tables, with the absolute time and the ratio of every variant in every scenario, are in [results/expected_benchmark.md](results/expected_benchmark.md); the main findings:

- **Size: the same.** In all 16 type pairs this library has the same `sizeof` as libstdc++'s `std::expected` (`sizes.csv` is unchanged by the storage fix described below); Outcome has it in 13 and is larger for `<char, unsigned char>` (6 against 2 bytes), `<string, text_error_t>` (72 against 40) and `<string, error_code>` (56 against 40). The layout of this library is a union and a flag, as the standard describes; the flag is a `bool` in a class as wide as the alignment of the union (`has_val_flag`), which changes no size.
- **Trivial copyability: a difference from libstdc++.** For types whose value and error are trivially copyable, `expected` of this library is trivially copyable (as [expected.object.cons] and [expected.object.assign]/5 of the current working draft say; the trivial assignments are not C++23 itself), `std::expected` of libstdc++ 13.2 is not (`std::is_trivially_copyable` is false for all 10 trivially copyable pairs of `sizes.csv`). Outcome is trivially copyable too.
- **Overall: on par with `std::expected`, with exceptions.** The geometric mean of the time ratio over the 37 scenarios, against `std::expected` C++23, is 0.997 for this library at C++23, 0.995 at C++20, 1.058 at C++17, 1.041 at C++14, 1.071 at C++11 and 1.147 for Outcome (31 scenarios; Outcome was measured at C++17 only, so compare its string rows with this library at C++17). Seven scenarios of C++23 are more than 10 % slower and six more than 10 % faster. Most of the single sub-nanosecond ratios are not properties of the library: the same loop lands at another place in each executable, and the numbers are stable between passes but not between executables. Example: `deref_int` is 0.38 ns at C++14 to C++23 and 0.51 ns at C++11, and the C++11 executable built with `-falign-loops=32` runs it in 0.37 ns (0.65 ns with `-falign-loops=1` or 16), with the same instructions in the loop.
- **Returning a trivially copyable `expected` through calls: fixed.** `return_chain_int` (four nested `noinline` calls returning `expected<int, unsigned>`) took 28.3 ns with this library at C++23 against 5.1 ns for `std::expected` (5.5 times, the same at all five standards) before the storage of the library was changed, and takes 5.3 ns now (1.04 times; 1.04 at C++20, 1.05 at C++17, 1.02 at C++14, 1.35 at C++11). The cause was found in the assembly and the counters. The storage is a base class of `expected`, and with a plain `bool` after a 4-byte union it ended in 3 bytes of tail padding that the Itanium ABI lets a derived class use; GCC 13.2 therefore built the 8-byte object, which is trivially copyable and returned in one register, through a stack slot (a 4-byte store for the value, a 1-byte store for the flag) and reloaded it with one 8-byte `movq` at every level, a store-to-load forwarding stall. The hardware counter `LD_BLOCKS.STORE_FORWARD` (event 0x03, umask 0x82 of the Golden Cove core, read with `perf_event_open` around the `return_chain_int` loop; the harness itself does not collect it) counted 20.15 million blocked loads for 20 million chains before the change (1.007 per chain) and 0 to 11 after; the instructions per chain fell from 54.9 to 42.0, the count of `std::expected`, and the cycles from 83 to 16 to 19 (`std::expected` 14 to 17). The machine code of the four levels and of the loop is identical to that of `std::expected` in all six executables (the same hash of the normalized disassembly), so the remaining differences between the executables, including the 1.35 at C++11, are code placement. The chain with a 12-character string (46 ns), a 64-character string (23 ns) and a 64-byte value (17.7 ns) is on par (0.96 to 1.04), because those objects are returned through memory. Two things were needed: the flag as a member class of the size of the alignment (`has_val_flag`), and `lumex_assert_handler` declared `noreturn`, because without it the always-on precondition check of `operator*` made GCC lay out the chain with the value path out of line and left it 1.4 times slower than `std::expected` even without the stall. Other compilers were not measured.
- **Strings: C++20 and newer are as fast as `std::expected`, older standards 35 to 43 % slower for short strings.** Construction, copy and assignment of a 12-character string are 1.35 to 1.43 times `std::expected` at C++11, 14 and 17 (3.5 against 2.4 ns for the copy), and 0 to 14 % at C++20 and C++23 (at C++23 the construction, copy and move loops compile to the same machine code as `std::expected`'s). Outcome at C++17 shows the same numbers, so this is the cost of `std::string` below C++20 in libstdc++ (the constructors are not `constexpr` and not as fully inlined), not of the library. For 64 characters (an allocation) the ratio is 0.88 to 1.14 and not distinguishable from noise.
- **Observers.** `has_value ()` is 0.36 ns per element (0.36 for `std::expected`). `value_int` and `error_int` are 1.35 to 1.42 times `std::expected` (0.50 against 0.37 ns) in most executables: the library checks the state in every call (`cmpb` and `jne` in the loop, the precondition of `error ()` and `operator*` with `LUMEX_ASSERT`, and the `value ()` test), the loop of `std::expected` has no test at all; `value_int` is 0.37 at C++14, which is the same loop at another place. `branch_mixed` (test, then dereference or take the error) reads 0.92 ns at C++14 to C++23 and 0.65 ns at C++11 and for `std::expected`; the machine code of the loop is the same before and after the storage fix and the cause was not established. `value ()` throws `bad_expected_access` on an error, as the standard says; `value_str12` (0.42 against 0.59 ns) and `value_or_mixed` (0.57 against 0.87 ns) are faster, but the code is the same as `std::expected`'s or differs only in placement: no claim.
- **Monadic operations: slower by 0 to 24 % at C++23.** `transform_int` 1.18 times, `and_then_int` 1.07, `or_else_int` 1.18, the three in a row 0.93, `transform_str12` (a `const` lvalue holding a string, the function reads its size) 1.02 at C++23 (0.82 at C++11). Outcome has no monadic members. The differences are small in absolute terms (0.1 to 0.2 ns per element).
- **Assignment.** Copy assignment, value over value `<int, unsigned>`, 0.76 times `std::expected` (0.73 against 0.96 ns), switching the alternative 0.61 (0.44 against 0.72 ns), a string value over a string value 1.13 at C++23, switching with strings 1.08 to 1.1.
- **The compile time is the price.** The unit of `compile_time.cpp` costs, over the same unit without the header (`-fsyntax-only -O0`, GCC 13.2): at C++11 +226 ms for this library (376 against 149 ms), at C++23 +417 ms for this library (730 against 312 ms) and +57 ms for `std::expected` (369 ms); Outcome at C++17 takes 878 ms. With `-c -O2`: lumex C++11 523 ms (no header: 164), lumex C++23 947 ms (no header: 334), `std::expected` 574 ms, Outcome 1 779 ms. The cost of this library rises with the standard (C++11 376, C++14 404, C++17 534, C++20 682, C++23 730 ms `-fsyntax-only`); the conversions to and from `std::expected` and the `-fno-exceptions` branches added about 40 to 100 ms; the cause of the rest (the `requires` branches and the headers the newer standards pull in) was not measured separately.

## Clang 23.1.0 with libc++

The same executables built with Clang 23.1.0 (`/opt/llvm-23.1.0`) and libc++, which the build picks by default (`LUMEX_CLANG_STDLIB` is `AUTO`; `std::expected` is the one of libc++), with the same flags of the Release profile, on the same machine, pinned to CPU 4, 5 passes, October 2026. The Clang rows are in the same CSV (`toolchain` `clang`), the tables in the `clang` sections of [results/expected_benchmark.md](results/expected_benchmark.md).

- **Overall on par, and the older standards are closer than with GCC.** The geometric mean of the time ratio over the 37 scenarios against `std::expected` C++23 is 1.009 for this library at C++23, 1.007 at C++20, 1.005 at C++17, 1.008 at C++14 and 1.066 at C++11 (GCC: 0.997, 0.995, 1.058, 1.041, 1.071); Outcome 1.151 over its 31 scenarios (GCC: 1.147). The scenarios more than 10 % slower than `std::expected`: 4 at C++23, 4 at C++20, 4 at C++17, 5 at C++14 and 6 at C++11 (GCC: 7, 7, 14, 12, 14); more than 10 % faster: 5, 6, 5, 6 and 5 (GCC: 6, 6, 6, 6, 5).
- **Rows more than 10 % off `std::expected` at C++23 with Clang.** Slower: `error_int` 3.08x, `deref_int` 1.47x, `transform_str12` 1.22x and `or_else_int` 1.14x; faster: `assign_switch_int` 0.53x, `assign_same_int` 0.82x, `copy_value_int` 0.84x, `copy_error_int` 0.87x and `copy_error_str12` 0.89x. The slow rows at the other standards are the same four (C++14 adds `chain_int` 1.11x); at C++11 the slow rows are `error_int` 3.06x, `return_chain_str12` 2.69x, `return_chain_str64` 2.38x, `deref_int` 1.47x, `return_chain_int` 1.21x and `or_else_int` 1.13x.
- **Where Clang differs from GCC.** `error_int` is 1.40x with GCC at C++23 and 3.08x with Clang, `deref_int` 1.06x and 1.47x; `value_int`, `branch_mixed` and `copy_error_int`, which GCC puts at 1.41x, 1.40x and 1.25x, are 1.00x, 1.01x and 0.87x with Clang. The string rows that cost 1.35x to 1.45x at C++11 to C++17 with GCC (`construct_value_str12`, `copy_value_str12`, `assign_same_str12`) are 0.99x, 1.02x and 0.83x at C++11 with Clang; instead `return_chain_str12` and `return_chain_str64` at C++11 are 2.69x and 2.38x with Clang, against 1.00x and 1.01x with GCC. Both compilers have `deref_int` at C++11 at 1.44x (GCC) and 1.47x (Clang), and both put `assign_switch_int` and `or_else_int` the same way (0.61x and 0.53x, 1.18x and 1.14x at C++23). No cause was investigated.
- **The layers.** The geometric mean of C++14, C++17, C++20 and C++23 over C++11 is 0.945, 0.943, 0.945 and 0.946 with Clang (GCC: 0.972, 0.988, 0.929, 0.931), so with Clang the four newer layers are alike and about 5 % faster than C++11.
- **Sizes.** With libc++ `sizeof (std::string)` is 24, so the five pairs that hold a `std::string` are smaller: 32 against 40 bytes for `<std::string, int>` in `std::expected`, in this library and in Outcome, and in Outcome 56 against 72 for `<std::string, text_error_t>` and 48 against 56 for `<std::string, std::error_code>` (`std::expected` and this library: 32 against 40 for both); every other `sizeof` and every property (trivially copyable, trivially destructible, standard layout, nothrow move) is the same as with GCC (`results/sizes.csv`).
- **Compile time with Clang** (median of 7; the stub without the header takes 156 ms at C++11 and 265 ms at C++23 with `-fsyntax-only -O0`, and 162 and 281 ms with `-c -O2`): with `-fsyntax-only -O0` this library takes 312 ms at C++11, 336 at C++14, 394 at C++17, 471 at C++20 and 680 at C++23, `std::expected` 312 ms and Outcome 667 ms (GCC: 376, 404, 534, 682, 730, 369 and 878 ms); with `-c -O2` 384, 412, 463, 564 and 785 ms for this library, 392 ms for `std::expected` and 798 ms for Outcome (GCC: 523, 554, 684, 911, 947, 574 and 1 779 ms).

## Caveats

- The numbers are for this machine and these two toolchains (GCC 13.2 with libstdc++, Clang 23.1.0 with libc++). They are not a promise about MSVC, Clang with libstdc++, other CPUs or other versions: run the benchmark there (`Running`). `std::expected` is that of libstdc++ 13.2 in the GCC rows and that of libc++ in the Clang rows; another standard library has another layout of the same type.
- The scenarios measure the type in a loop with the optimizer held back by empty `asm` statements. They show the cost of the interface, not of a whole program, and a fraction of a nanosecond is one or two instructions or cycles.
- Outcome is configured with `policy::terminate` (checked observers). Its default policy for an arbitrary error type would not check, which would make `value ()` cheaper and unsafe; and Outcome's `ok`/`err` in the scenarios use `in_place_type`.
- Six scenarios are not run for Outcome (`value_or` and the five monadic ones): it has no such members and none was emulated.
- `std::expected` and this library differ in what a precondition violation does: `operator*` and `error ()` of this library abort through `LUMEX_ASSERT` in every build; the standard leaves it undefined (libstdc++ asserts only with `_GLIBCXX_ASSERTIONS`), which is part of what the observer rows measure.
- No result of this run carries a dagger (the passes of every result agree within 25 %).
