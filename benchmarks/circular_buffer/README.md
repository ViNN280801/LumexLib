# circular_buffer benchmarks

The ring buffer of this library (`lumex::core::circular_buffer::circular_buffer`) against `boost::circular_buffer` of Boost.CircularBuffer and against what a user writes without a ring library: `std::deque` used as a bounded queue (`pop_front` before `push_back` when full) and `std::vector` with manual index math (head and size, the wrap done by a compare and a subtraction, and a second variant that wraps with `%`, the way this library computed its physical index before it was changed to a compare). All five run the same scenarios from the same source. The buffer of this library and `boost::circular_buffer` are measured at C++11 and at C++17; the three plain alternatives at C++17. The library was changed after the first measurement (the run-time division of the index, the per-element copy and four memory defects; see "What changed" below) and the numbers here are from the changed library; the numbers of the earlier library are kept in [results/circular_buffer_benchmark_before_rework.csv](results/circular_buffer_benchmark_before_rework.csv). Only one toolchain was measured: GCC 13.2.0 with libstdc++. Clang with libc++ was not measured (the build supports it: a second build tree with `--build-dir clang=...`), so nothing here says how Clang or MSVC compile the same code.

The numbers behind the chart: [results/circular_buffer_benchmark.md](results/circular_buffer_benchmark.md) (raw data: [results/circular_buffer_benchmark.csv](results/circular_buffer_benchmark.csv), footprint: [results/circular_buffer_footprint.csv](results/circular_buffer_footprint.csv)).

## What the alternatives are

| Variant | What it is |
| --- | --- |
| lumex | `circular_buffer<T>` of this library |
| boost | `boost::circular_buffer<T>` 1.92.0, headers only |
| deque | `std::deque<T>` plus a capacity: `push_back` pops the front first when full. The bounded queue a user gets from the standard library. |
| vector | `std::vector<T>` of `capacity` elements, head and size, `wrap (i) = i >= capacity ? i - capacity : i`. A full buffer overwrites by assignment. Elements are never destroyed by `pop_front` or `clear`, so `T` must be default constructible and a popped `std::string` keeps its buffer. |
| vector % | the same with `wrap (i) = i % capacity`, which is how this library computed its physical index before it was changed. It exists to show what the division costs. |

`deque`, `vector` and `vector %` are about 100 lines (`bench_circular_buffer_impl.hpp`), keep only the members the scenarios use and are not a published container. They are not a claim about the best possible hand-written ring.

## Method

- One source, `bench_circular_buffer.cpp`, compiled once per implementation and standard with `-DBENCH_RING_IMPL=1..6` (`bench_circular_buffer_impl.hpp` maps it to the buffer under test). Every variant is built with the same flags of the Release profile of the library (`-O2 -DNDEBUG -march=x86-64 -mtune=generic` and the library warnings); there are no sanitizers. The build has no warnings.
- Scenarios (the unit of an operation is in the description column of the results): `push_back` into a full buffer (overwrite) for `int`, a short `std::string` (small-buffer) and an 80-character `std::string` (heap); the steady state of a queue (`push_back`, read `front`, `pop_front`) on a half-full buffer; `clear` and `size` `push_back` into a buffer that never gets full; the same followed by draining with `front` and `pop_front`; `front ()` and `back ()` of a wrapped buffer; a sum over 768 elements of a wrapped buffer by `operator[]` and by iterators; a producer and a consumer on one thread (bursts of 1 to 8 pushes and up to 7 pops per step, 1 024 steps, capacity 256, so the buffer fills and overwrites); construction and destruction of an empty buffer of capacity 1 024; copy construction, copy assignment and a move construction followed by a move assignment back, each for `int` and `std::string`. "Wrapped" means the head is not at the start of the storage: 1.5 times the capacity is pushed and a quarter popped.
- Equal work: before timing, every scenario is run for a few iterations and its checksum is compared with the same scenario run on a reference container (a `std::vector` that erases its first element when full, obviously correct). The checksums are written to the CSV and `run_benchmark.py` compares them across all executables; different checksums stop the run.
- The optimizer is kept from deleting or hoisting the work with empty `asm` statements that read the buffer object (`"m"`) and clobber memory. The scenarios keep the buffer in a local variable; the barrier forces its members to be stored and reloaded at the marked points in every implementation alike (the disassembly of the `push_back` loop of this library shows the stores and reloads of the size and the head every iteration).
- A scenario is calibrated until one run lasts at least 20 ms, then runs once as warm-up and 15 times for the numbers. The CSV keeps the median, the minimum and the maximum time per operation of the 15 repetitions; `run_benchmark.py` runs every executable `--passes` times (here 5), one pass over all executables after the other, and keeps, per scenario, the lowest of the pass medians (the best pass), the highest of them (shown only as the spread: a dagger marks a value whose slowest pass was more than 25 % slower), the smallest minimum and the largest maximum. In this run four values carry a dagger, all of the `vector` ring (`push_pop_steady_str_short`, `fill_int`, `fill_str_short`, `move_pair_str_short`); none of this library's or Boost's does, and the largest spread is 1.34x (`push_pop_steady_str_short`, `vector`).
- The process is pinned to one CPU with `taskset` (`--cpu 3`).
- Every timing run was made under the build lock of the workstation, so the machine was otherwise idle.
- The baseline of the ratios is `boost::circular_buffer` at C++17 (the first column; the first of `boost C++17`, `vector C++17` that was measured when Boost is absent). The size column is the capacity; the copy scenarios hold 3/4 of it. Every table cell is the absolute time in nanoseconds of the best pass and, in parentheses, the ratio to the baseline (below 1.00 is faster than `boost::circular_buffer`).
- Footprint (`--traits`): `sizeof` of the container and the bytes and calls requested from `operator new` after construction, after 10 and after 1 024 `push_back` (capacity 1 024), for five element types. The executable replaces the global `operator new` with a counting `malloc` wrapper in every variant alike; the count is only switched on in this mode.

## What changed

The first measurement of this library (committed in [results/circular_buffer_benchmark_before_rework.csv](results/circular_buffer_benchmark_before_rework.csv), geometric mean 2.77 against Boost) found one 64-bit `div` per element in the index math and an element-by-element copy. An experiment on a header copy with only the three `%` replaced by a compare measured a geometric mean of 1.18. The library was then changed: the three index computations are a compare and a subtraction, and the copy constructor and copy assignment copy in at most two contiguous pieces. Four memory defects were fixed at the same time (reuse of a moved-from buffer, aliasing pushes, leaks when a copy throws, copy assignment between unequal allocators; one of them, the aliasing fix, adds a temporary to an overwriting push, which the numbers below include) and the Boost interface was extended (`insert`, `erase`, `resize`, `set_capacity`, `assign`, ...). The experiment build (`lumex compare-wrap`) is gone from the benchmark because the library itself now has the compare. The `vector %` ring stays as the measurement of what a run-time division costs.

## Boost

Boost is optional and header-only: the boost variants need `boost/circular_buffer.hpp` and are skipped, with a message, when CMake finds none. Pass the include directory with `-DLUMEX_BENCH_BOOST_INCLUDE_DIR=<dir>` or point `find_package(Boost CONFIG)` at an installation. Nothing of Boost is linked or vendored. On the workstation of the committed results Boost 1.92.0 is installed in `/opt/boost-1.92.0` (only its headers are used); the system also has Boost 1.67 in `/usr/include`, which was not used.

## Running

```sh
cmake -S . -B build-bench-gcc -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_COMPILER=g++ -DLUMEX_BUILD_BENCHMARKS=ON \
      -DLUMEX_BENCH_BOOST_INCLUDE_DIR=/opt/boost-1.92.0/include
cmake --build build-bench-gcc --target LumexCircularBufferBench_lumex_cxx11 \
      LumexCircularBufferBench_lumex_cxx17 LumexCircularBufferBench_boost_cxx11 \
      LumexCircularBufferBench_boost_cxx17 LumexCircularBufferBench_deque_cxx17 \
      LumexCircularBufferBench_vector_cxx17 LumexCircularBufferBench_vector_mod_cxx17
python benchmarks/circular_buffer/run_benchmark.py --build-dir gcc=build-bench-gcc --cpu 3
```

`run_benchmark.py` writes `results/circular_buffer_benchmark.csv`, `results/circular_buffer_footprint.csv` and, through `plot_results.py` (Python standard library only), the Markdown table and the SVG chart. The target `LumexCircularBufferBenchmarkRun` runs the executables of one build tree and writes into that build tree, so it never overwrites the committed results.

## Reading the results

Measured on an Intel Core i7-12700K (Linux 6.1, pinned to one performance core), GCC 13.2.0 with libstdc++, Boost 1.92.0 (headers only), 5 passes, October 2026. 29 scenarios. The full table is in [results/circular_buffer_benchmark.md](results/circular_buffer_benchmark.md).

- **This library is within 1.04x of `boost::circular_buffer` as a geometric mean (lumex C++17 against boost C++17; 1.05x for C++11 against C++11), slower by more than 10 % in 7 of 29 scenarios and faster in 4** (before the change: 2.77, 21 slower, 1 faster). Against the `vector` ring the geometric mean is 1.092 (7 slower, 6 faster), against the `deque` 0.779 (9 slower, 17 faster). Within 1.3x of Boost in 24 of 29 scenarios; the five above 1.3x are `push_overwrite_str_long` (2.13x), `push_overwrite_str_short` (1.88x), `front_back_str_short` (1.54x), `iterate_sum_str_short` (1.48x) and `front_back_int` (1.42x); `iterate_sum_int` is 1.29x.
- **The division is gone.** The physical index is `head + i`, minus the capacity when that reaches it (a compare and a conditional move); in the disassembly of the GCC 13.2 probe loops of this library (`operator[]`, iteration, `front () + back ()`, the overwriting push) there is no integer `div`. Before, one `div` per element cost about 2.4 ns here. Now `index_sum_int` takes 275.4 ns for 768 elements (before 1 809 ns; Boost 281.3 ns), `push_pop_steady_int` is 1.03x of Boost (before 7.51x), `fill_drain_int` 1.06x (7.54x), `fill_int` 1.11x (3.50x), `push_overwrite_int` 0.36x (2.63x, 0.76 ns against 2.13 ns). The `vector %` ring, which still divides, shows what remains of that cost: `index_sum_int` 1729 ns, `iterate_sum_int` 1765 ns.
- **Copying.** Copy construction and copy assignment copy the content in at most two contiguous pieces: 768 `int` take 178.6 ns to copy-construct (0.79x of Boost; before 15.85x) and 186.1 ns to copy-assign (0.79x; before 15.32x). The `vector` ring, which copies once into storage it already owns, is faster (56.13 and 34.29 ns); for 96 `std::string` of 80 characters copying is at par with Boost (0.91x and 0.94x), and the `vector` ring and the `deque`, which assign into the strings they already hold, are 5.3x faster at copy assignment (407.0 and 412.3 ns).
- **Iteration and `front () + back ()` stay slower (1.3x to 1.5x of Boost).** The library keeps a head and a size and wraps the index with a compare and a conditional move on every access; Boost keeps first and last pointers and wraps only when it steps a pointer. Hardware counters (user-space instructions and cycles read with `perf_event_open` in a probe program built with the benchmark's flags; three runs) give 15 instructions for `front () + back ()` against 11 in Boost (the loop of this library has the loads of the head, the size, the capacity and the slot pointer and the `mov`, `sub`, `cmp`, `cmovae` of the wrap), 2.8 against 1.8 to 2.3 cycles; 9 instructions per element for iteration against 7, 1.5 to 2.0 against 1.2 cycles; and 9 instructions per element for `operator[]` against 12 in Boost (the reason `index_sum_int` is at par). The hand-written `vector` ring with a compare is as slow as this library in the same scenarios (`front_back_int` 1.43x, `iterate_sum_int` 1.27x of Boost): the cost belongs to the head-and-size representation.
- **Overwriting a string is slower than Boost, which assigns.** The oldest element is destroyed and the new one constructed. The probe counts, per overwriting push of an 80-character string, 259 instructions and 1 heap call against 83 instructions and none for Boost; for a short string 106 against 75 instructions. The `vector` ring, which assigns, is at par with Boost (3.74 and 6.01 ns). The new element is built in a temporary before the old one is destroyed (so that pushing an element of the buffer itself is safe and a throwing constructor leaves the buffer unchanged); a header copy that destroys first needs 78 instructions for the short string and 247 for the long one, so the temporary accounts for about 28 and 12 instructions, and the rest is destroy-and-construct against assign. The `deque`, which also destroys and constructs, takes 2.53x of Boost for the long string.
- **Where this library is on par or ahead of Boost:** copying `int` (above), `push_overwrite_int` (0.36x), move construction plus move assignment (3.30 ns against 3.32 ns, `int`; `deque` is 7.6x slower because the move constructor of libstdc++'s `std::deque` is not `noexcept` and allocates a map for the moved-from deque), construction and destruction of an empty buffer (`ctor_dtor_int` 0.97x; one `malloc` and one `free` of 4 096 bytes for both, and run alone in a process of its own both took about 14.7 ns in the earlier measurement, so differences of this kind come from the heap state the scenarios before leave), `producer_consumer_*` (1.04x and 1.02x), `push_pop_steady_*` (1.03x for `int`, 0.99x for the long string) and `index_sum_*`.
- **Plain alternatives:** the `vector` ring with a compare is within 0.47x to 1.09x of Boost in the three `push_overwrite` scenarios and 0.92x in `index_sum_int`, but 1.27x to 1.46x slower in the iterator sums and 1.43x to 1.51x in `front_back`. It is 32.0x slower in `ctor_dtor_str_short` (684.3 ns against 21.36) because it constructs 1 024 `std::string` up front, so it also needs a default constructible `T`. The `deque` is 0.76x to 2.53x of Boost in the push scenarios, 1.0x to 1.9x in the traversals, 7.6x in `move_pair_int`, and uses 88 bytes for the object and blocks that grow with the content (the footprint table). It is the only variant that does not allocate the whole capacity up front (576 bytes in two calls when empty, 4 816 bytes in 11 calls at 1 024 `int`).
- **C++11 build against C++17 build of this library:** geometric mean 1.001, no scenario more than 10 % apart (0.97x to 1.02x).
- **Layout.** `sizeof` of the container is 40 bytes for this library and for Boost, 48 for the `vector` rings and 88 for the `deque`, whatever `T`. The heap block of this library and of Boost is exactly `capacity * sizeof (T)` in one call (4 096 bytes for 1 024 `int`), nothing more; unchanged by the rework.
- **Compile time** was not measured.

## Caveats

- The numbers are for this machine and this compiler, one toolchain (GCC 13.2.0, libstdc++). The cost of the compare-and-conditional-move wrap and of the instruction counts above depends on the CPU; none of this was measured on another machine or on another compiler. The earlier library divided; the 64-bit `div` of this CPU cost about 2.4 ns, and older cores are slower.
- The scenarios measure a buffer in a loop with the optimizer held back by empty `asm` statements. They show the cost of the interface, not of a whole program.
- `deque`, `vector` and `vector %` are written for this benchmark and are not tuned beyond the wrap; a different hand-written ring (a power-of-two capacity with a mask, which needs a different API) would be faster than all of them.
- The unit of the pass scenarios is a whole pass; divide by the element count for a per-element time.
- Boost 1.92.0 was built with the system GCC 8, but only its headers are used.
